# 风控规则变更业务验证：从人工写 SQL 到模板化 + Agent 评估

> 系列：AI SRE 实践笔记 · 02
> 范围：规则变更后的业务影响验证
> 状态：线上运行
> 配套实践：[风控规则变更业务验证：工程实现](../practice/02-风控规则变更业务验证.md)

## 一、问题

### 1.1 场景

风控规则是风控业务的核心逻辑，调整很频繁：阈值调整、新增规则、规则下线、逻辑修改，每周甚至每天都有。每次调整之后都要先验证——用数据跑一遍，确认影响在预期内，才敢放量。

这里说的验证是**业务验证**：变更对业务结果的影响，也就是命中量、误杀漏杀、资损、客诉这些维度，而不是规则本身能不能跑通。

现在的验证链路大致是这样：

```
规则变更 → 业务研发提供验证逻辑（临时写 SQL） → 跑数 → 人工分析结果 → 判断影响是否在预期内 → 放量或回滚
```

规则本身改起来很快，链路上真正花时间的是后两段：等验证逻辑，和看结果。

### 1.2 痛点

1. **验证逻辑跟不上规则迭代。** 每来一次变更，业务研发就要按这次变更临时写一套 SQL 或脚本。规则一周改三次，验证逻辑就得跟着写三次，还得排期。验证成了变更链路上的串行瓶颈：不是规则不好改，是改完没法快速确认能不能上。
2. **结果解读全靠人，评估不到位。** 跑出来的是命中量、命中率、金额、案件明细几张大表。人看结果，时间有限，通常只盯一两个总量指标，看到「总量变化不大」就过了。但结构变化往往藏在总量底下——总量没变，命中的可能是另一批人；拦截量没变，放行案件的金额分布却变了。这类问题人眼看不出来，也说不清。
3. **验证知识不复用。** 每次验证都是一次性的，SQL 跑完就丢。相似类型的变更，下一个人还要重写一遍；同一个问题，不同人验证的口径可能还不一样。经验没有沉淀成资产。

### 1.3 根因：验证被做成了两个一次性的人工环节

规则变更的影响本质上是一个**数据事实**。但当前链路上，有两个关键环节是纯人工前置：

- **写验证逻辑**：本应是「这一类变更该看哪些指标」的知识，现在被写成了「这一个变更的 SQL」。知识没有沉淀，每次都从零开始。
- **解读结果**：工具只给了数字，没给对比、没给归因。人脑一次只能看两三个维度，剩下的就漏了。

所以问题可以拆成三个：

- **验证什么**：这类变更的影响面由哪些指标刻画？
- **怎么验证**：用哪批数据、和什么基线比、怎么保证可比？
- **结果怎么读**：哪些变化是真信号，哪些是业务自然波动？影响是否在预期内？

前两个是确定性的数据和工程问题，适合模板化，用 SQL / 聚合回答；第三个需要业务语义和上下文，是 LLM 擅长的。

方案因此落在两件事上：**验证逻辑模板化 + 参数化**，把「验证什么、怎么验证」沉淀成可复用资产；**结果评估交给 Agent**，把「结果怎么读」从人工经验变成带证据的判断。

## 二、思考

### 2.1 为什么是「模板化 + Agent」

| 方案 | 靠什么 | 主要问题 |
| --- | --- | --- |
| 每个变更临时写 SQL | 一次性人工 | 交付慢、不可复用、口径因人而异 |
| 一套固定验证逻辑 | 固定指标 | 覆盖不了不同类型的变更，个性化诉求无解 |
| 只有模板，不接 Agent | 模板产出数字 | 解读仍靠人，评估质量不变 |
| 纯 LLM 看数据做判断 | 模型 + 原始数据 | 数字不可信、口径不清、不可复核 |
| **模板 + Agent** | 模板保证口径与可比性，Agent 负责解读与归因 | 模板需要持续维护；影子流量有覆盖上限 |

关键差别在于分工：模板保证**数字怎么来**——口径确定、可复核；Agent 负责**数字怎么读**——对比、归因、给结论。这两件事不能互相替代：让模型自己算数会错，让人读所有数字会漏。

### 2.2 关键工程判断：先算数，再解读

**Agent 不计算。**

所有指标都由模板里的 SQL / 聚合先算好：新旧规则的命中量、命中率、人群分布、金额分布、翻转案件数，等等。Agent 拿到的是算好且口径明确的聚合结果，加上本次变更说明和历史基线。

模型只做四件事：找异常维度、解释可能原因、对照 rubric 给结论、引用数字写报告。

原因很实在：LLM 做聚合计算不可靠，算错了从报告上也看不出来；一旦让模型自己算，口径就开始漂。把计算固定在模板里，报告里每个数字都能回溯到一条 SQL，结论才可复核。

### 2.3 模板抽象的是「验证问题」，不是 SQL

模板按变更类型切，不按规则切：

| 变更类型 | 核心验证问题 | 关键指标 |
| --- | --- | --- |
| 阈值调整 | 命中量放大或收缩多少？集中在哪些人群？ | 命中量、命中率、分数分布、人群结构 |
| 新增规则 | 新增命中里多少原本会放行？误杀怎么估？ | 新增命中量、人群画像、与存量规则的重叠度 |
| 规则下线 | 原本拦下的有多少放行？敞口多大？ | 释放量、释放金额、释放案件抽样 |
| 逻辑修改 | 哪些案件判定翻转？翻转方向是否合理？ | 翻转量、翻转方向、翻转案件样本 |

每个模板 = 指标集合 + 对比方式 + 参数（规则 ID、场景、时间窗、分群维度、阈值）+ 预期区间的表达方式。

个性化靠参数承接：同一模板换分群、换时间窗、换阈值即可。参数覆盖不了的特殊诉求，降级为自定义 SQL，但必须登记入库，作为下一轮模板演进的候选。这样「模板覆盖率」就成为一个能盯的指标——它决定了这套东西能覆盖多少变更。

### 2.4 影子运行的前提是「可比」

验证方式是影子运行：同一时间窗内，新规则旁路跑一遍线上请求，结果只落库、不影响线上判定，再和旧规则结果对比。

几个容易忽略的点：

- **必须同一批请求、同一时间窗双跑。** 拿今天的新规则结果和上周的旧结果比，等于把流量结构变化、业务活动、外部数据变化全都算进了「规则影响」，结论不可信。
- **隔离副作用。** 影子命中的案件不能真的触发拦截、发审核单、调下游。隔离没做好，影子运行本身就会污染线上。
- **外部依赖也在变。** 规则依赖的名单、模型分、额度数据同样在更新，双跑只能控制规则维度。变更窗口要避开这类数据更新，或者在报告里显式标注。
- **长尾场景样本不足。** 低频规则在影子窗口里的样本可能只有几十条，这时「没有异常」往往是因为「没有样本」。指标必须带样本量和置信区间，样本不足时结论是「不可判定」，而不是「无影响」。

### 2.5 「是否在预期内」必须定义清楚

这是整件事最容易含糊的地方。只给 Agent 一堆指标让它判断「影响大不大」，结论会随样本漂移，人也没法复核。所以要先有三样东西：

1. **结构化的变更说明**：这次变更想做什么、预期命中增加多少、针对什么人群、什么情况算不可接受。没有预期，「是否在预期内」就无从谈起——这是最容易被省略、又最关键的一项输入。
2. **评估 rubric**：按命中量与命中率、误杀与漏杀、资损与金额、客诉与体验四个维度，分别定义正常波动、需关注、需阻断三档，并写清每个指标怎么算。
3. **结论分级**：可放量 / 需观察 / 需人工复核 / 建议回滚。Agent 输出的是建议和证据，放不放量由人签字。

rubric 由风控策略同学和验证 / SRE 共同维护，写下来、可评审、可版本化。它的价值不止是让 Agent 结论稳定，更是把「什么算影响可控」这个团队里一直靠口头共识的问题固定下来。

### 2.6 误判成本不对称

漏报（有影响的变更被判成正常）意味着带病放量，代价是资损和客诉，而且往往不可逆；误报（正常变更被判成有风险）只是多一次复核、晚放量半天，成本有限。

所以评估的目标是**召回优先**：宁可多报，不能漏报。但要配合降噪和分级——所有变更都报「需人工复核」，很快就会没人看，召回也就名存实亡。合理做法是高置信风险直接升级，中低风险进观察列表，不阻塞放量。

### 2.7 长期风险：模板和口径腐化

这套方案里最容易过期的不是 Agent，是模板和口径。

- 业务口径一变（新增分群、调整统计范围），模板还按老口径跑，数字对、结论错。
- 模板要版本化，指标口径要登记，模板库要有人负责。
- 定期用历史上的真实变更做回测：拿当时已知的影响，检验模板和 rubric 能不能识别出来，识别不出来的就是模板该补的洞。
- Agent 本身也要稳定：固定 Prompt 版本、固定输出 schema、temperature=0。同一份数据多次评估结论应当一致，否则它就是一个不稳定的运营对象。
- 影子运行有覆盖上限：没有流量的场景就验证不了，这类变更仍需人工兜底。

## 三、收益与衡量

收益不在于「AI 比人判断得准」，而在三点：验证逻辑从一次性人力变成可复用资产；评估从人看表变成带证据的报告；验证知识第一次被沉淀下来。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 验证方案就绪时延 | 规则变更 → 验证逻辑可用 | 直接反映研发排期瓶颈是否解除 |
| 端到端时延 | 规则变更 → 评估结论 | 决定验证能否跟上规则迭代 |
| 模板覆盖率 | 用模板完成的验证 / 全部验证 | 衡量资产的复用程度 |
| 人工介入率 | 需要人工复核的变更占比 | 决定长期人力投入 |
| 漏报率 / 误报率 | 对照真实影响，评估结论的对错 | 漏报对应资损风险，误报对应人工负担 |
| 单次验证成本 | 人力 + 计算 / 次 | 决定能否覆盖全部变更 |

受数据敏感性限制，本文不披露具体业务数值。以上指标在团队内部持续跟踪，用来看方案是否真的解开了原先那两个瓶颈，而不是只看「有没有报告」。

从线上运行的链路看，验证已经从「每次等研发写 SQL」变成「规则变更后自动产出评估报告」，人的时间主要从跑数、看表转到写清预期和维护模板。这个方向能不能长期成立，仍然取决于模板覆盖率和影子数据的质量——这两项是后面最该盯的。

## 四、结论

问题的本质不是「怎么让人验证得更快」，而是验证一直是以一次性劳动的方式在做：逻辑一次性、结果一次性、经验也一次性。

一句话总结：**把验证逻辑沉淀成模板资产，把结果解读交给带证据的 Agent，人从「写 SQL 和看表」退到「定义预期和维护规则」。**

下一步继续推进的三件事：

1. 模板库扩充——从历史变更和自定义 SQL 里反推模板，把覆盖率提上去；
2. 影子运行的数据质量与可比性，特别是外部依赖变化和长尾样本；
3. rubric 能不能真正落地——「影响可接受」是组织共识问题，不是技术问题。
