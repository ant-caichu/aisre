# 变更类操作识别：从「人脑打标」到「代码给证据」

> 系列：AI SRE 实践笔记 · 01
> 状态：小范围验证
> 配套实践：[变更类操作识别：工程实现](../practice/变更类操作识别.md)

## 一、问题

### 1.1 场景

SRE 的变更风险运营大致是一条链：

```
有哪些操作 → 哪些会改变线上状态 → 风险分级 → 管控策略（审批/灰度/熔断/观察/回滚）
```

第一条「有哪些操作、哪些是变更类操作」是后面所有动作的前提。标错了，后面整套管控都是在错误的地图上做决策。

我们已有的信息来自 SDK：应用、方法名、方法描述。之前的做法是 SRE 拿着这三样东西人工打标，判断这个方法是不是变更类操作。落地下来，投入很大，效果很差。

### 1.2 痛点拆开看

「投入大、效果差」其实是四件事叠在一起：

**信息不足。** 方法名和描述是作者对意图的压缩，不是对行为的描述。命名不规范、描述为空或过期、`handle`/`process`/`commonXxx` 这类方法大量存在时，SRE 手上的信息几乎不足以做判断，只能靠猜和靠记忆。

**覆盖率低。** 人力只能覆盖被点名的重点应用和重点接口。长尾应用没人标，新应用上线没人标，标了的应用迭代几次就过期。风险地图天然有洞。

**时效错配。** 人工标注是快照式、周期式的，而业务是持续迭代的。风险运营的节奏永远追不上业务迭代速度，这不是加人能解决的。

**没有反馈闭环。** 标错了不会有人告诉你。漏标一个写操作，直到它真的引发故障才可能被发现。判断质量无法度量，也无法改进。

几个典型的失效模式：

| 方法名 / 描述 | 实际行为 | 人工容易怎么判 |
| --- | --- | --- |
| `getOrderDetail` | 内部懒加载库存并回写缓存 | 只读（漏判） |
| `queryAndSync` | 查询后同步写库 | 只读（漏判） |
| `updateUser` | 只更新内存对象或写审计日志 | 变更（误判） |
| `handle` / `process` | 描述为空，实际写多张表 | 无法判断 |
| `refreshConfig` | 改的是本地缓存，不是线上配置 | 变更（误判） |

### 1.3 为什么人工打标注定效果差

不是 SRE 不努力，而是这个任务本身把判断依据放错了地方。四个结构性错配：

1. **信息维度错配。** 判定需要的是「方法执行后会不会改变线上状态」，这是一个代码事实；而输入只有名字和描述，这是作者意图的摘要。用二维信号做高维判断，天花板很低。
2. **知识位置错配。** 真正知道方法干了什么的人是不写文档的研发；有判定责任的人（SRE）不掌握代码上下文。人工标注本质上是在用 SRE 的隐性记忆去补偿缺失的代码事实。
3. **成本结构错配。** 人工成本随「应用数 × 迭代次数」线性增长，而风险运营要求随变更实时。这两条曲线不可能相交。
4. **责任与激励错配。** 研发没有打标动机，SRE 标错无成本。没有反馈闭环，质量不会自我修正。

### 1.4 重新定义问题

把「这是什么操作」拆成三个可计算的子问题：

- **副作用**：方法最终是否触达一个会改变状态的操作（写库、发消息、改配置、调外部写接口……）
- **可达性**：从方法出发，经过调用链能不能到达那个副作用，中间隔着几层封装、是否在条件分支或异步回调里
- **业务语义**：这个副作用在业务上算不算「变更」（写审计日志算吗？删缓存算吗？幂等写算吗？）

前两个是代码结构问题，正好是调用图 / 知识图谱擅长的；第三个需要读实现、需要业务理解，是 LLM 擅长的。

所以问题从「给方法名做文本分类」变成了「**图上的可达性分析 + 语义裁决**」。这个转换是整套方案成立的前提。

## 二、思考

### 2.1 为什么是「知识图谱 + Agent」

| 方案 | 信息来源 | 主要问题 |
| --- | --- | --- |
| 人工打标 | 名字 + 描述 + 个人经验 | 覆盖低、时效差、不可度量、知识随人流失 |
| 命名/注解规则 | 方法名、`@Transactional`、SQL 关键字 | 跨层封装（Service→Manager→DAO）、动态 SQL、RPC 透传导致规则永远补不完；准确率天花板明显 |
| 研发写代码时加注解 | 作者本人 | 推行成本高、老代码无注解、可漏可绕过；适合做辅助信号，不适合做唯一来源 |
| 纯 LLM 看名字和描述 | 与人工相同的两三个字段 | 输入信息没有变，只是换了个更会编的主体；不可解释 |
| **图谱 + Agent** | 代码实现、调用链、入口类型 | 成本与工程复杂度更高；动态特性有盲区 |

关键差别不在模型，而在**信息维度**：前四种方案用的都是「关于代码的描述」，图谱 + Agent 用的是「代码本身」。准确率提升的来源是信息变多了，不是模型比人聪明。

同时，图谱给了 Agent 一个天然的好处：判定结果可以带证据链（哪个方法、哪一行、经过哪条调用路径触达了哪个写操作）。这让结果可复核、可申诉、可归因，而不是一个黑盒标签。

### 2.2 一个关键工程判断：先反向可达，再问模型

如果对每个方法都组装上下文去问 LLM，成本是 O(方法数)，一个中等规模的公司就是几十万到上百万次调用，既贵又慢，「近实时」无从谈起。

更合理的做法是先用图做一次性的**反向可达性分析**：从所有副作用节点出发，沿调用图反向遍历，给每个方法算出一个结构分——是否可达写操作、最短距离几跳、路径上有几个写节点、是否只在异常分支里可达。

然后分流：

- 直接写、1~2 跳可达写 → 大概率是变更类，抽样校验即可
- 不可达任何写操作 → 大概率只读，抽样校验
- 3 跳以上、条件写、只经过缓存写、路径语义模糊 → **灰区，交给 Agent**

LLM 只需要处理灰区。成本从 O(方法数) 降到 O(灰区数)，通常是一个数量级的下降。**「近实时」是靠这个结构筛选取得的，不是靠模型推理变快。**

### 2.3 判定准则必须显式化

「变更类操作」不是一个自明的概念。如果不把边界写清楚，Agent 的判定会随样本漂移，人也没法复核。我在实践里倾向把它做成**多标签**而不是二分类，因为下游管控策略不同：

- 数据写入（增删改、状态流转）
- 配置 / 开关变更
- 流量 / 路由变更
- 权限 / 账号变更
- 消息投递（MQ、事件、通知）
- 外部写调用（跨应用）

几个必须提前定下来的边界：

| 情形 | 我的倾向 | 理由 |
| --- | --- | --- |
| 只写审计 / 访问日志 | 不算变更 | 不改变业务状态；但若审计本身是合规要求，应单独归类 |
| 幂等写、dry-run、补偿逻辑 | 看是否真的推进状态 | 幂等不代表无副作用，要读实现 |
| 读操作触发懒加载 / 缓存回写 | 算变更（轻度） | 线上可观测行为会变 |
| 缓存删除 / 刷新 | 算变更（轻度） | 会影响下游读路径与数据库压力 |
| 读取开关 | 不算 | 无状态改变 |
| 修改开关 | 算 | 典型配置变更 |
| 幂等令牌写入 | 通常不算业务变更 | 属于基础设施行为 |

这些判断不应该藏在 Prompt 的例子里，而应该成为一份**可评审的 rubric**，由 SRE 和研发共同维护。它的价值不只是让模型更准，更是让「什么算变更」这个组织内一直模糊的问题第一次被写下来。

### 2.4 误判成本不对称

漏判（把变更类标成只读）意味着这个操作完全脱离管控，风险敞口是无限的；误判（把只读标成变更）只是多一层审批，成本有限。

所以优化目标应该是**召回优先**，而不是追求一个好看的准确率数字。具体做法：

- 输出置信度而不是硬标签，阈值可调
- 高置信自动入库，中置信抽样，低置信进人工队列
- 人工的角色从「全量标注」变成「灰区复核 + 规则维护」

这也顺带解决了人力问题：人工投入随灰区规模变化，而灰区会随着 rubric 和样本积累逐步缩小。

### 2.5 最大的长期风险不是模型，是图谱腐化

如果代码知识图谱不能随代码实时更新，半年后它和人工标注一样过期，只是过期得更贵。这是这个方案能否长期成立的分水岭。

所以方案的核心组件其实不是 Agent，而是**把图谱更新挂进研发流水线**：

- 代码合并 / 发布事件触发增量索引
- 只重算受影响的子图（变更方法本身 + 其上游调用者），而不是全量扫描
- 缓存「方法体 hash → 判定结果」，方法没变就不重判
- 维护 SDK 上报版本与代码 commit 的对应关系，否则会出现「拿新版代码判断旧版行为」

真正要度量的是**端到端时延**：从代码合并到风险标签可用，而不是模型单次推理耗时。前者决定了风险运营能不能跟上业务节奏。

### 2.6 与线上行为数据结合：下一步

静态分析有天然盲区：反射、动态代理、脚本、配置驱动的调用。这些靠图谱补不齐。

但线上数据可以补一部分：trace、SQL 审计、写流量。有写流量的方法**一定**是变更类，这是高置信的正样本；没有写流量则不能反推为只读（可能只是没被调用到）。用这种弱标签去校准和扩充金标集，是一个成本很低、收益明确的方向。

### 2.7 还没想清楚的问题

- **粒度**：方法级还是入口级？一个 HTTP 接口内部调了多个方法，风险评估应该按入口聚合还是按方法展开？我目前倾向「方法级判定 + 入口级聚合展示」。
- **动态语言与框架**：反射、SPI、AOP、动态 SQL 的可达性精度能到多少？会不会出现「图上不可达但线上确实写了」的系统性漏判？
- **判定稳定性**：同一方法多次判定是否一致？需要 temperature=0、固定 Prompt 版本、维护回归集，否则 Agent 本身就是一个不稳定的运营对象。
- **责任划分**：rubric 谁维护？判错了谁负责？当「变更类」成为发布前置条件，误判会不会阻塞正常发布？需要申诉通道和 dry-run 能力。
- **跨应用写**：A 调 B 的写接口，A 的变更性依赖 B 的标签。这需要应用间依赖图和标签传播，是单仓图谱解决不了的，可能是下一阶段的主要工作量。

## 三、收益与衡量

我们的收益不应该表述为「AI 比 SRE 准」。更准确的表述是：

1. **信息维度**：从 2 个字段（名字、描述）变成代码实现 + 调用链 + 证据
2. **成本结构**：从随迭代线性增长的人力，变成一次性建设 + 边际成本趋近于零
3. **时效**：从周 / 月级的运营节奏，变成随代码合并实时产出
4. **可运营性**：从不可解释的标签，变成带证据链、可复核、可回填判断

对应的度量指标：

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 漏判率 / 召回 | 人工金标中变更类被正确识别的比例 | 主指标，直接对应风险敞口 |
| 准确率 | 判为变更类的样本中确实为变更类的比例 | 控制误判带来的人工负担 |
| 覆盖率 | 已给出判定的方法 / 应覆盖的方法（含实体对齐率） | 风险地图的完整性 |
| 端到端时延 | 代码合并 → 标签可用 | 决定能否匹配业务迭代节奏 |
| 人工复核占比 | 进入人工队列的比例 | 决定长期人力成本 |
| 单位方法成本 | tokens + 计算 + 人力 / 方法 | 决定能否全量铺开 |

定性结论：小范围验证表明，从「名字 + 描述」切换到「代码实现 + 调用链」后，准确率和时效都有明显改善，且判定结果可以给出证据链。这个方向的假设初步成立。

## 四、结论

这个问题的本质不是「怎么让人标得更快」，而是**判断依据放错了地方**。变更性是一个代码事实，应该由代码回答。

一句话总结：**把藏在人脑里的隐性知识，变成写在代码里的显性证据；人从标注者变成规则维护者和例外处理者。**

下一步要验证的，不是模型还能不能更准，而是两件工程问题：
1. 图谱更新能不能真正挂进流水线，做到增量、实时、不腐化；
2. 跨应用写调用的标签能不能传播，把单仓的局部正确拼成全局正确。
