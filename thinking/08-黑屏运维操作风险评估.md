# 黑屏运维操作风险评估：从「命令流水」到「可还原、可反查的操作场景」

> 系列：AI SRE 实践笔记 · 08
> 范围：堡垒机黑屏命令的场景还原、风险洞察与应急反查
> 状态：线上运行
> 配套实践：[黑屏运维操作风险评估：工程实现](../practice/08-黑屏运维操作风险评估.md)

## 一、问题

### 1.1 场景

基础运维和 DBA 申请到堡垒机权限后，大部分操作通过黑屏完成：SSH 登录主机改配置、起停服务、清理磁盘，或者连上数据库执行 SQL。堡垒机会记录每条命令，包括操作人、目标主机、时间和会话 ID。

风险就在这里：权限一旦给出，命令层面几乎没有约束。堡垒机解决了「谁在什么时候登了哪台机器」，但没解决「他到底做了什么、这组操作意味着什么」。

目前对这批命令的使用方式是：留着，出事时翻。

### 1.2 痛点

1. **单条命令没有意义，一组命令才是场景。** `cd /etc/nginx`、`cp nginx.conf nginx.conf.bak`、`vim nginx.conf`、`nginx -t`、`systemctl reload nginx` 单独看都是普通命令，连起来才是一次配置变更。审计日志按命令存，风控需要按操作看。
2. **数量决定了人工评估不可行。** 日均数千条命令，逐条看不可能；抽样检查覆盖率低，而且抽到的往往是正常操作。靠人盯，等于没有评估。
3. **事后溯源靠翻日志。** 故障发生时，知道某台主机在某个时间点异常，但要回答「谁在这之前改了什么」，得按主机和时间去捞命令，再靠人把命令串起来。这个过程慢，而且容易漏掉跨会话、跨主机的操作。

第 2 点和第 3 点是同一个问题的两面：**数据是按命令存的，而人需要的是按场景看。**

### 1.3 根因：缺一层「操作场景」的还原

堡垒机日志的粒度是「一条命令」：

```
时间, 操作人, 目标主机, 会话ID, 命令
```

风控和溯源需要的粒度是「一次操作」：

```
谁, 在什么时间, 对哪个对象, 做了什么场景的操作, 由哪些命令组成
```

这两者之间差一步还原：把同一次会话里的命令按操作切段，识别每段的对象和意图，再判断这组操作的风险。没有这一步，无论是日常洞察还是应急反查，都只能停留在命令级别。

还有一个现实约束：这些黑屏操作**关联不到变更工单**。相当一部分操作是应急、临时排查、代班，本来就没有工单。所以方案不能建立在「和审批比对」上，只能基于操作本身、对象重要性、行为基线和时间上下文来判断。

## 二、思考

### 2.1 先定边界：这是洞察与溯源，不是实时管控

黑屏是应急通道，很多操作天然发生在故障处置过程中。如果做成实时阻断，会有两个后果：一是误判直接卡住排障，二是很快出现绕过手段（换通道、传脚本、用交互式工具规避命令记录）。

所以定位是：

| 能力 | 做不做 | 原因 |
| --- | --- | --- |
| 事后场景还原 | 做 | 这是所有能力的基础 |
| 日常风险洞察与改进建议 | 做 | 解决「没人看」的问题 |
| 应急时按对象反查操作 | 做 | 解决「翻日志慢」的问题 |
| 实时告警 | 有限做 | 只对极高危命令模式提示，不阻断 |
| 实时阻断 | 不做 | 误判成本高，且会被绕过 |
| 判定违规 | 不做 | 没有工单和输出，只能给信号，不能下结论 |

这个边界很重要。把「风险信号」包装成「违规判定」，短期看起来很强，长期会失去使用者的信任。

### 2.2 场景还原的三层结构

| 层 | 输入 | 输出 | 方法 |
| --- | --- | --- | --- |
| 会话 | 同一 session_id 的命令序列 | 按时间排序的完整操作过程 | 直接聚合 |
| 操作段 | 会话内的命令序列 | 若干连续命令组成的操作段 | 空闲间隔、对象切换、命令族变化、路径变化 |
| 场景 | 操作段 + 目标对象 + 操作人 | 对象 + 动作 + 意图 | 规则 + 模型归纳 |

**切段信号**：

- 相邻命令的时间间隔超过阈值（人在思考、在等执行结果）
- 目标路径或服务发生跳转（从 Nginx 目录切到系统日志目录）
- 命令族切换（从文件操作切到服务管理，再切到数据库客户端）
- 出现明确的边界命令（`exit`、`cd /`、重新登录）

**场景分类**（初期够用即可）：巡检、配置变更、服务启停、发布部署、数据查询、数据变更、备份恢复、故障处置、权限与账号、其他。

关键是**对象识别**：主机要归一到资产 ID，数据库要归一到实例和库表。同一条命令在不同对象上的风险完全不同，`rm -rf` 在临时目录和在生产数据目录是两件事。

### 2.3 没有工单，风险靠什么判断

没有「预期操作」这个参照，就只能从四个维度看：

| 维度 | 看什么 | 例子 |
| --- | --- | --- |
| 对象重要性 | 资产等级、承载业务、是否核心链路 | 核心库执行 DDL |
| 命令危险度 | 不可逆、影响面大、绕过审计 | `rm -rf`、`drop table`、改防火墙、清空日志 |
| 场景合理性 | 操作时段、操作人权限范围、操作对象是否属于其负责范围 | 凌晨对非本人负责的主机做配置变更 |
| 行为基线 | 该操作人历史习惯、该对象的常规操作 | 首次在某类对象上执行某类操作 |

这四维组合出来的是**风险信号**，不是结论。比如「DBA 在凌晨对核心库执行了 DDL」是一个明确信号，但它可能是计划内发布，也可能不是——报告要写清楚观察到了什么，而不是替人下判断。

### 2.4 只有命令、没有输出，结论要相应收敛

当前能拿到的只有命令、操作人、目标主机、时间、会话 ID，没有终端输出，也没有文件传输记录。这意味着：

- **无法判断命令是否执行成功。** 报告只能写「执行了 X」，不能写「X 导致了 Y」。
- **无法看到交互式操作的内容。** `vim`、`mysql` 之后的输入不一定以命令形式记录，场景还原会缺一块。
- **无法确认实际影响对象。** 命令里的路径、库表名可能有变量，只能标为「声称的对象」。

所以输出措辞要严格：**「观察到」「疑似」「需人工确认」，而不是「已导致」「违规操作」。** 应急查询也一样，给的是时间线相关性，不是因果结论。

### 2.5 成本决定了不能逐条分析

日均数千条命令，全部交给模型逐条理解，成本和时延都不现实，也没有必要——绝大多数命令是重复的、正常的。

分层处理：

1. **规则与指纹**：命令归一化后聚类，高频模式直接归类，不调模型。
2. **会话级模型归纳**：只对切段后的操作段做场景识别，不逐条调用。
3. **深度分析**：只对高风险信号、异常会话、被应急查询命中的会话做更细的还原。
4. **抽样复核**：每天抽一部分正常会话做质量校验，防止规则和模型一起漂移。

这样大部分成本落在「会话」而不是「命令」上，量级从每天数千条降到每天数百个会话。

### 2.6 应急查询是另一个入口，不是附属功能

日常洞察和应急查询用的是同一份场景索引，但查询路径不同：

- **日常**：按风险信号排序，看「今天有哪些需要关注的操作」。
- **应急**：按对象 + 时间窗反查，看「这个对象在这段时间被谁、按什么顺序改过」，输出操作时间线。

应急场景对时延和召回更敏感：宁可多列一些相关会话，也不能漏。所以索引要同时支持「对象 → 时间 → 会话 → 操作段 → 命令」和「人 → 对象 → 时间」两条路径，并且保留原始命令，供人核对。

### 2.7 误报的代价在这个场景里是信任

黑屏操作里，正常运维占绝大多数。如果每天报出上百条「高风险」，运维团队很快就会把它当成噪音，连带真正重要的信号一起忽略。

所以策略是：**高风险信号少而准，中等风险做汇总，低风险只入库不打扰。** 每条信号必须能指到具体命令和具体对象，让人一眼能判断是不是自己干的、是不是计划内。判断不了的时候，降级为「待确认」，而不是升级为「高危」。

### 2.8 数据本身很敏感

命令里经常带密码、连接串、内网地址、业务数据。方案要默认：

- 入库前脱敏，密码类参数一律替换
- 查询结果按对象和团队控制可见范围
- 所有查询行为本身要留审计
- 模型调用前再过一遍敏感信息过滤

## 三、收益与衡量

收益有两块。日常侧，把「没人看的命令日志」变成「按场景组织的操作视图」，能持续发现配置漂移、权限越界、危险操作习惯，产出改进建议。应急侧，把「翻日志拼时间线」变成「按对象直接查」，缩短定位时间。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 场景还原准确率 | 抽检中对象、动作、场景判断正确的比例 | 所有上层能力的基础 |
| 会话切分准确率 | 操作段边界与人工标注一致的比例 | 切错段，场景必然错 |
| 高风险信号准确率 | 被复核确认的比例 | 决定是否有人看 |
| 高危操作覆盖率 | 已知高危操作被识别出的比例 | 对应真实风险 |
| 应急查询命中率 | 故障反查中能找到相关操作的会话占比 | 衡量溯源有效性 |
| 平均定位时长 | 从发起查询到拿到可用时间线的时间 | 应急场景的核心指标 |
| 改进建议采纳数 | 被运维团队实际采纳的条数 | 衡量洞察是否产生价值 |
| 查询覆盖率 | 接入堡垒机的对象占比 | 决定视图是否完整 |

按对象类型、操作人角色、时段分层看。总体准确率高但核心库和高危命令系统性漏报，是最危险的情况。

受数据敏感性限制，本文不披露具体业务数值。

## 四、结论

问题的本质不是「命令没人审」，而是审计数据的粒度和风控需要的粒度不一致。命令日志回答的是「执行了什么」，风控要回答的是「谁对什么对象做了什么操作、这组操作是否正常」。

一句话总结：**先把命令还原成操作场景，再在场景层面做风险信号和应急反查；不追求实时阻断，追求看得清、查得快、说得准。**

下一步的重点不在模型，而在三件基础工作：

1. 资产与对象的归一化——决定场景能不能落到正确的对象上；
2. 会话切分与命令指纹的质量——决定成本和准确率；
3. 风险信号的人工复核闭环——决定这套东西会不会变成没人看的报表。
