# 数据库 SQL DDL 变更风险识别和提示：从「DBA 凭经验」到「AI 先审、DBA 确认」

> 系列：AI SRE 实践笔记 · 06
> 范围：MySQL 主从单库的 DDL 变更评估
> 状态：线上运行
> 配套实践：[数据库 SQL DDL 变更风险识别和提示：工程实现](../practice/06-数据库DDL变更风险识别和提示.md)

## 一、问题

### 1.1 场景

DDL 变更是数据库变更里风险最高的一类。它直接改表结构，影响查询性能、锁、主从复制和磁盘空间，一旦出问题就是业务异常，而且不像代码那样容易回滚。

现在的流程大致是：

```
DDL 工单提交 → DBA 审核 → 低峰执行 → 观察
```

审核这一步，靠 DBA 同时判断三件事：这条 DDL 执行起来会锁多久、要多久；对现有查询和索引有什么影响；这张表有多少数据、被哪些业务在用、当前负载多高。

### 1.2 痛点

1. **判断依赖个人经验，信息还分散。** 表有多大、索引基数多少、谁在查、慢查询长什么样、主从延迟余量多少——这些信息散在数据库、监控、慢日志和业务系统里。DBA 审核时往往只能临时查一部分，剩下的靠经验拍。
2. **人工评估是被动的，深度不稳定。** 工单来了才看，时间紧，注意力还要在常规变更和高风险变更之间分配。大表加索引、改字段类型这类真正需要仔细算的变更，经常要靠反复沟通才能说清。
3. **历史教训不沉淀。** 上一次这张表加索引锁了多久、上次改类型导致复制延迟了多久，这些经验留在 DBA 脑子里。换个人、过一阵子，同样的坑再踩一次。

用户给的判断很准确：风险高，但评估被动。问题不在 DBA 不专业，而在于评估所需的信息量和分析成本，已经超过了一个人在审核窗口内能稳定完成的程度。

### 1.3 根因：DDL 风险是「语句 × 表状态 × 业务负载」的组合问题

单独看 SQL 语句，只能判断语法和操作类型；单独看表，只能知道大小和索引。真正的风险出现在三者交叉的地方：

- 给一张几千万行的表加索引，和给一张几万行的表加索引，是完全不同的两件事。
- 删一个索引，如果它是某个慢查询的唯一可用索引，风险不在 DDL 本身，而在那条查询。
- 改字段类型，风险取决于表的写入量、主从延迟余量和是否 online。

所以评估要同时回答三个问题：

- **DDL 本身怎么执行**：锁类型、是否 rebuild、预计耗时、空间放大。
- **对现有负载有什么影响**：索引与执行计划变化、慢查询、写入放大、复制延迟。
- **影响面有多大**：数据量、业务重要性、调用方、变更窗口。

前两个偏数据库结构，第三个偏业务数据。人做这件事的瓶颈是信息收集和交叉分析，不是专业知识本身——这正是可以交给机器的部分。

## 二、思考

### 2.1 为什么是 Agent + 数据库元数据，而不是规则或静态分析工具

| 方案 | 靠什么 | 主要问题 |
| --- | --- | --- |
| DBA 人工评审 | 经验 + 临时查库 | 信息收集慢，判断不一致，完全依赖个人 |
| 规则引擎 | 固定红线（禁 drop、禁改类型） | 只能挡已知问题，组合风险判断不了 |
| 静态 SQL 分析工具 | 语法与执行计划 | 不知道数据量和业务流量，结论要么保守要么失真 |
| 纯 LLM 看 SQL | SQL 文本 | 不知道表多大、谁在用，只能给通用建议 |
| **Agent + 元数据 + 历史** | 表结构、数据量、慢查询、QPS、版本参数、历史变更 | 依赖元数据质量；MySQL 版本与 online DDL 能力要对准 |

关键差别在于信息：DDL 风险是「语句 × 表状态 × 业务负载」的组合，只看语句永远得不到结论。规则能覆盖红线，覆盖不了组合判断；模型能理解组合，但必须先把事实喂给它。

### 2.2 关键工程判断：先算清事实，再让模型判断

表行数、数据大小、索引基数、QPS、慢查询、磁盘余量、主从延迟、MySQL 版本和参数——这些是**确定性事实**，必须从元数据和监控里算出来，不能让模型猜。

模型负责的是把事实和 DDL 语义关联起来：

- 这条 DDL 在当前 MySQL 版本下是什么执行方式，会不会 rebuild
- 受影响的索引正被哪些查询使用，删掉之后有没有替代索引
- 按当前数据量和写入量，执行多久、锁多久、复制延迟大概多少
- 这次变更的业务影响面有多大，应该放在什么窗口执行

耗时的估算可以用规则 + 经验系数（基于行数、DDL 类型、版本、硬件），给出区间并写明依据。**模型不生成数字，只解释数字。** 一旦让模型自己估，报告里的时间和容量就不可复核，而这类错误从结论表面根本看不出来。

### 2.3 评估维度要覆盖完整

| 维度 | 关注点 |
| --- | --- |
| 执行风险 | 锁类型与持锁时长、是否 rebuild、预计耗时、临时空间与磁盘放大 |
| 性能风险 | 索引变化、执行计划变化、慢查询恶化、写入放大 |
| 容量与复制 | 数据量、磁盘余量、binlog 量、主从延迟 |
| 业务影响 | 表被哪些业务使用、QPS、是否核心链路、变更窗口 |
| 可回滚性 | 是否可逆、新旧代码兼容、执行顺序 |
| 操作规范 | 是否低峰、是否分批、是否有备份与回滚脚本 |

维度不全是常见问题。只看执行耗时，会漏掉「执行很快但删错了索引」；只看索引，会漏掉「索引没问题但主从扛不住 binlog 量」。

### 2.4 分级与阻断的边界

高风险要阻断，但阻断不能全交给模型：

| 判断来源 | 示例 | 处置 |
| --- | --- | --- |
| 硬规则 | 磁盘余量不足以支撑 rebuild、核心表高风险操作、高峰期执行大表 DDL | 阻断 |
| 硬规则 | 删除被慢查询使用的索引、改类型涉及大表且无回滚方案 | 加签或强制确认 |
| 模型判断 | 组合风险、业务影响评估、执行窗口建议 | 提示或建议加签 |
| 信息缺失 | 元数据拉取失败、版本未知 | 不可判定，转人工 |

硬规则负责确定性强、后果明确的情况；模型负责解释和组合判断。冲突时以硬规则为准。

阻断必须有申诉和豁免通道，豁免要留痕。阻断太多的直接后果是流程被绕过——把变更拆小、线下先执行、换个说法，这些比漏报更隐蔽。

### 2.5 误判成本不对称，但方向和别的场景不同

漏报的代价很直接：锁表、复制延迟、慢查询，业务当场受影响，而且 DDL 回滚成本高。

误报的代价是 DBA 反复确认、流程变慢。单次成本不高，但累积起来会让人开始忽略提示，最后变成「反正都要点确认」。

所以这里的分级策略是：**高风险维度从宽（宁可阻断），提示维度从严（没有证据不报）。** 不能为了覆盖率把每一条 DDL 都标成需要关注。

### 2.6 最大的长期风险：元数据和数据库状态失真

评估依赖的是快照，而数据库是活的：

- 表大小和行数在变，评估时和实际上线时可能差很多
- 索引、统计信息、QPS 都在变
- MySQL 版本和参数决定 online DDL 能力，版本信息错了，结论就全错
- 主从延迟和磁盘余量是瞬时的，执行前必须再看一眼

所以执行前要做一次二次校验，而不是信评估时的那份快照。另外，历史 DDL 案例要有结构（表、操作、耗时、锁、影响），不能只是一堆文档。

### 2.7 协作模式的变化

AI 负责第一遍全量审核：按维度收集事实、分析组合风险、给出证据和建议。DBA 负责确认：业务判断、例外处理、最终签字。

这不是把 DBA 替换掉，而是把 DBA 从「收集信息和初步分析」里解放出来，把时间花在真正需要判断的地方。责任边界不变：AI 出报告，DBA 签字。

## 三、收益与衡量

收益不在于「AI 比 DBA 懂数据库」，而在于：每一条 DDL 都能在提交后立刻得到一份基于完整信息的评估；DBA 的审核从「从头查一遍」变成「确认结论」；历史经验第一次可以被检索和复用。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 评估覆盖率 | 接入评估的 DDL / 全部 DDL | 决定风险地图是否完整 |
| 高风险识别率 | 真实高危 DDL 被标记为阻断或加签的比例 | 核心指标，对应业务事故 |
| 误报率 | 被 DBA 判定为误报的比例 | 决定流程是否会被绕过 |
| 豁免率 | 阻断后被豁免的比例 | 过高说明规则过严或流程失效 |
| 审核时长 | DDL 提交 → DBA 确认 | 衡量是否真的提效 |
| 端到端时延 | 提交 → 报告产出 | 决定能否嵌入现有工单流程 |
| 变更后故障率 | DDL 执行后引发业务异常的比例 | 最终效果 |
| 回滚率 | DDL 执行后被迫回滚的比例 | 辅助判断评估质量 |

受数据敏感性限制，本文不披露具体业务数值。

## 四、结论

问题的本质不是「DBA 审得慢」，而是 DDL 风险评估需要的信息量和交叉分析成本，已经超出人工审核窗口能稳定处理的范围。

一句话总结：**让系统先把数据库事实和业务影响算清楚，AI 按维度审一遍，DBA 只做业务判断和最终确认。**

下一步要处理的不是模型能力，而是三件基础工作：

1. 元数据的新鲜度与准确性——决定结论可不可信；
2. MySQL 版本与 online DDL 能力库——决定执行风险估得准不准；
3. 执行前的二次校验与历史案例沉淀——决定这套评估能不能长期站得住。
