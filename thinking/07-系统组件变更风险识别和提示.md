# 系统组件变更风险识别和提示：从「给个预案链接」到「直接给出这次变更怎么做」

> 系列：AI SRE 实践笔记 · 07
> 范围：DNS、ELB 等基础设施组件的变更方案与风险提示
> 状态：线上运行
> 配套实践：[系统组件变更风险识别和提示：工程实现](../practice/07-系统组件变更风险识别和提示.md)

## 一、问题

### 1.1 场景

DNS、ELB、CDN、证书、网络设备这类系统组件，处在流量入口和基础设施的关键位置。它们的变更有个共同特点：操作本身不复杂，但影响面大，而且出错之后不容易局部回滚。

比如改一条 DNS 记录，TTL 是提前设好的，改错了解析会持续指向错误地址；摘除 ELB 后端，顺序不对会把流量打到还没准备好的实例上；证书更新，时间窗口没算好就是全站不可用。这类变更的风险不在命令本身，而在对象、顺序、窗口和影响面。

现在的 ITSM 流程是：

```
变更人提交工单 → 审批页给出变更预案的跳转链接 → 审批 → 变更人自行执行
```

### 1.2 痛点

1. **知识给了入口，没给答案。** 链接指向的是一份通用预案，变更人要点开、找到对应章节、判断哪几条适用于本次变更。审批窗口只有几分钟，实际结果就是没人点，或者点了也不看。
2. **通用文档和具体变更之间差一次翻译。** 手册写的是「ELB 后端摘除流程」，本次变更要回答的是「这个 CLB 下的这三个后端，在今晚这个窗口，按什么顺序摘、摘完看什么、出问题怎么加回去」。这一步翻译过去靠人，现在还是靠人。
3. **熟练度门槛没降下来。** 非常规变更、新人、跨团队代班，是最容易出问题的场景，也恰恰是最需要指引的场景。历史故障的教训停在复盘文档里，没有进入下一次变更的操作过程。

### 1.3 根因：缺的不是知识，是「知识到动作」的转化

把问题拆开看，中间断了两段：

- **知识 → 本次方案**：从多份手册、预案、复盘里，筛出与当前对象和场景相关的部分，裁剪成一份可执行的方案。
- **方案 → 执行动作**：把方案变成有顺序、有校验点、有中止条件、有回滚路径的操作清单。

链接模式只解决了「知识存在哪里」和「从哪里进入」，这两段转化都留给了变更人。而这两段恰好是最费时间、最依赖经验的部分。

所以方案的重点不是再建一个文档库，而是把「检索 + 裁剪 + 组装」这一步做掉，直接输出这次变更能用的东西。

## 二、思考

### 2.1 几种做法的差别

| 做法 | 输出 | 主要问题 |
| --- | --- | --- |
| 审批页放预案链接 | 文档入口 | 需要人自己找、自己判断，实际打开率低 |
| 文档站搜索 | 文档列表 | 关键词匹配，不理解变更对象和场景 |
| 知识库问答 | 一段回答 | 通用性强，但不针对本次变更，也没有执行顺序和校验点 |
| **按变更画像组装方案** | 步骤、风险、回滚、通知 | 依赖知识库质量；对象和场景识别要准 |

差别在于输出物。前三者输出的是「知识」，变更人需要的是「这次怎么做」。这两者之间差的不是模型能力，是对象、场景、窗口、业务重要性这些上下文有没有被用上。

### 2.2 输出应该是什么形态

一份能直接用的变更指引，至少包含四块：

| 部分 | 内容 | 回答的问题 |
| --- | --- | --- |
| 操作步骤 | 前置检查、按序步骤、每步的校验点和中止条件 | 先做什么、后做什么、做到哪算成功 |
| 风险防控 | 结合对象属性、时间窗口、业务重要性的注意事项 | 这次变更特别容易在哪出事 |
| 回滚方案 | 触发条件、回滚顺序、回滚后验证、时间上限 | 出问题怎么退，退到什么程度算退干净 |
| 影响与通知 | 受影响的业务、通知对象、变更前后通告 | 谁会受影响，什么时候告诉谁 |

这四块里，**操作步骤和回滚必须来自知识库原文**，模型只能筛选、排序、补齐上下文，不能自己发明命令。这是这个场景和一般问答最大的区别：输出会被人直接照着执行，一条编造出来的命令就是一次事故。

### 2.3 事实和知识要分开

- **事实**来自工单：变更对象（域名、记录类型、TTL；LB 实例、监听、后端组、权重）、变更场景（新增、修改、摘除、扩容、证书更新）、时间窗口、关联业务及其重要性、变更人所属团队。
- **知识**来自知识库：运维手册、变更预案、故障复盘与事件记录。
- **模型**做的是匹配、裁剪、排序和解释，把知识和事实对上，而不是生产知识。

这条边界决定了两件事：第一，模型不能补全工单里没有的架构信息，比如「这个域名背后还有哪些系统在用」，没有依据就不写；第二，知识库里没有的操作，宁可空着并提示联系组件负责人，也不要用通用经验补。

### 2.4 全量组件接入的真正难点：知识密度不均匀

DNS、ELB 这类高频组件，手册和复盘都比较完整；长尾组件可能只有一份几年前的手册，甚至连手册都没有。如果对所有组件用同一套生成逻辑，结果就是：核心组件输出质量尚可，长尾组件一本正经地胡说。

所以全量接入的前提是先给组件分级：

| 等级 | 知识状况 | 输出策略 |
| --- | --- | --- |
| A | 有完整 SOP + 历史复盘 + 明确的回滚方案 | 输出完整四段方案 |
| B | 有 SOP，复盘较少 | 输出步骤和回滚，风险提示标注「基于手册，缺少历史案例」 |
| C | 只有零散文档或旧手册 | 只输出检索到的原文片段和待确认项，不组装完整方案 |
| D | 没有可用知识 | 不生成方案，直接给出组件负责人和升级路径 |

分级不是为了少做，而是为了让「不知道」显性化。让变更人看到「这个组件我们没有足够知识」，比给一份看似完整、实则不可靠的方案要安全得多。

### 2.5 个性化要克制

个性化来自工单字段，不是来自推测：

- 对象属性决定参数：域名和记录类型决定要改哪些记录；TTL 决定回滚生效时间；LB 的监听和后端组决定摘除范围。
- 时间窗口决定风险等级：高峰期做入口类变更，提示要更严。
- 业务重要性决定通知范围和是否需要灰度：核心业务要求提前通知、分批操作、有人在岗。

不做的事：不推断未填写的依赖关系，不假设「应该还有其他调用方」，不根据业务名称猜重要性。字段缺失就在报告里标出来，让变更人补。

### 2.6 对话追问的边界

审批页生成方案之后，允许变更人继续追问，比如「为什么要先摘这两个后端」「如果健康检查一直失败怎么办」「能不能提前半小时做」。

追问的价值是澄清和补全上下文，不是扩展知识边界：

- 能答的：方案里的步骤依据、风险原因、回滚细节、影响范围。
- 不能答的：知识库里没有的操作、其他组件的架构事实、对未填写字段的推测。
- 答不了就明确说知识库中没有，并给出负责人。追问记录本身就是知识缺口的线索。

### 2.7 错误指引比漏报更危险

一般风险识别场景里，漏报和误报要权衡。这个场景的权衡不一样：

- 漏一条提示，变更人可能凭经验也能过。
- 编一条错误步骤，变更人会直接执行，后果是现成的。

所以策略是：**宁可少写，不可编造；没有依据就降级到原文或转人工。** 所有步骤和风险都要能追溯到手册章节或复盘编号，让变更人可以核对。这也顺带解决了信任问题——变更人不是盲信 AI，而是在核对一份已经整理好的材料。

### 2.8 人的位置没变

AI 生成的是建议方案，变更人确认后执行，审批流照旧。对核心组件，审批人仍然要看方案和风险提示。

变化在于：变更人从「找文档、读文档、判断适用性」变成「核对方案、补充本团队的信息」；审批人从「凭经验判断变更人靠不靠谱」变成「看方案是否覆盖了关键风险」。责任边界没变，做判断所需的信息变完整了。

## 三、收益与衡量

收益不在于「AI 比老运维更懂 DNS」，而在于：每一次系统组件变更都能在提交后拿到一份针对本次对象和场景的方案；手册和复盘第一次真正进入执行环节；新人做非常规变更时不再完全依赖身边有没有熟手。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 方案覆盖率 | 生成方案的变更 / 全部系统组件变更 | 决定接入是否完整 |
| 知识支撑率 | 有明确引用来源的方案占比 | 衡量方案是否可信 |
| 方案采纳率 | 变更人确认或按方案执行的占比 | 决定方案是否有用 |
| 追问率与追问解决率 | 发起追问的变更占比 / 追问得到有效回答的比例 | 衡量方案完整度和对话价值 |
| 变更失败率 | 执行失败或触发回滚的比例 | 最终效果 |
| 变更时长 | 提交 → 执行完成 | 衡量是否真的提效 |
| 知识缺口数 | 降级为 C/D 的组件与场景数量 | 驱动知识建设 |
| 引用错误率 | 抽检中发现引用不存在或与原文不符的比例 | 底线指标 |

按组件类型、业务等级、变更人经验分层看。总体采纳率高但 C/D 级组件被强行生成方案，是最危险的情况。

受数据敏感性限制，本文不披露具体业务数值。

## 四、结论

问题的本质不是文档不够多，而是知识停在「可查阅」的状态，没有走到「可执行」的位置。

一句话总结：**用变更对象、场景、窗口和业务重要性把知识库里的内容筛出来、裁剪好，直接给变更人一份可核对的步骤、风险和回滚方案，人负责确认和签字。**

下一步的重点不在模型，而在三件基础工作：

1. 组件知识的分级与缺口盘点——决定哪些组件能生成完整方案，哪些只能给原文；
2. 手册和复盘的结构化程度——决定检索和引用能不能准；
3. 引用可追溯与抽检机制——决定变更人敢不敢照着做。
