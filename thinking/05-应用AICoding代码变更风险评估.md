# 应用 AI Coding 代码变更风险评估：从「人工审不动」到「AI 先诊断、人做确认」

> 系列：AI SRE 实践笔记 · 05
> 范围：AI Coding 产出的代码在合入前与发布前的风险评估
> 状态：小范围验证中，数据待补
> 配套实践：[应用 AI Coding 代码变更风险评估：工程实现](../practice/05-应用AICoding代码变更风险评估.md)

## 一、问题

### 1.1 场景

越来越多的业务应用把 AI Coding 作为主要开发方式。开发效率的提升是实打实的，但代码产出快了，评审和发布风险评估的节奏并没有跟着变：

```
需求 → AI 生成 / 修改代码 → 人工 CodeReview → 合入 → 发布评审 → 上线
```

后面这几段，原本都建立在一个前提上：**有人读过这段代码，并且读得懂**。AI Coding 把这个前提打破了。

### 1.2 痛点

1. **代码产出量和变更频率超出人工评审的消化能力。** MR 数量、单次改动体积、提交频率都在涨，评审时间反而被压缩。结果就是评审退化成看标题、扫一眼 diff、点通过。不是评审人不负责，是物理时间不够。
2. **AI 写的代码「读不懂」，而且不是语法层面的读不懂。** 生成出来的代码通常结构清晰、命名规范、能跑通，看起来比人写的还整齐。问题在于它可能隐含了对业务约束、现有封装、并发模型、历史踩坑的误解——比如在一个有并发上限的链路里新加了一次同步远程调用，代码本身完全合法，但会打穿整个容量假设。评审者没有时间去重建这些上下文，也说不清哪里不对。
3. **传统风险控制手段都在同一个前提下失效。** 静态扫描只能抓语法和已知模式，抓不到业务语义；单测覆盖的是 AI 自己写的用例，覆盖率高不代表理解正确；变更评审依赖评审人的经验，而评审人面对的是一批自己不熟悉的代码。

### 1.3 根因：评审的供给和代码的产出来自同一个瓶颈

代码由 AI 批量生产，评审仍然是一个人一个人地读。AI 把供给侧的速度提上来了，消费侧还在原地，这个差距不会靠「加强评审意识」补上。

更根本的是，判断一段代码的风险需要的信息，本来就不全在 diff 里：

- 这次改动的需求意图和验收标准
- 这个方法和接口被谁调用、影响到哪些入口
- 相关模块之前出过什么问题
- 测试覆盖了什么、没覆盖什么

这些信息分散在需求系统、代码仓库、调用链、测试平台和故障库里。人有时间的时候也未必能拼齐，何况现在没时间。

所以问题拆成四步：

- **看懂改了什么**：需求意图、diff、改动范围
- **判断会影响什么**：调用链、上下游、数据与配置
- **判断哪里可能出错**：稳定性、逻辑、安全、可运维性四类风险
- **决定怎么办**：确认风险、补测试、加保护、回滚方案

前三步是信息处理，机器比人快得多；第四步是责任判断，仍然要人来做。

## 二、思考

### 2.1 为什么是「AI Agent + 代码知识图谱」

| 方案 | 靠什么 | 主要问题 |
| --- | --- | --- |
| 人工 CodeReview | 人的经验和时间 | 吞吐不够，上下文不足，面对陌生代码判断力下降 |
| 静态扫描 / SAST | 规则和模式 | 只覆盖已知模式，不理解业务语义，误报多 |
| 单测与覆盖率 | 测试用例 | AI 先写实现后补测试，覆盖不等于正确 |
| 纯 LLM 看 diff | 模型 + diff | 看不到调用链和历史，只能给通用建议，容易编造 |
| **Agent + 代码图谱 + 多维上下文** | diff、需求、调用链、测试、历史故障 | 依赖图谱质量；最终判断需要人确认 |

单看 diff，能做的是「代码品味」评审——命名、结构、异常处理。接上图谱和历史数据，才能回答真正重要的问题：这段改动会不会影响某个关键接口？会不会重演上个月那类故障？测试到底覆盖了哪些分支？

### 2.2 关键工程判断：分两层介入，不做一次性终审

风险评估接在两个位置，目标不同：

| 时机 | 关注点 | 特点 |
| --- | --- | --- |
| MR 合入前 | 代码本身的问题：空指针、并发、事务边界、资源泄漏、越权 | 反馈快，改起来便宜；看不到线上影响 |
| 发布前 | 这次发布对线上的影响：影响入口、容量、依赖、历史故障 | 上下文全，结论更准；此时阻断代价高 |

两层共用同一套检查项和证据格式，但阈值不同。合入前可以更敏感，因为误报的代价只是研发改一改；发布前要更克制，因为阻断会直接影响发布窗口。

只做发布前，问题发现太晚，修复成本最高；只做合入前，看不到线上影响，容易漏掉「代码没问题但这次时机不对」的风险。

### 2.3 判断依据必须显式化

四类风险维度要落成可检查的条目，而不是靠 Prompt 里的几个例子：

| 维度 | 典型检查项 |
| --- | --- |
| 稳定性与性能 | 循环内远程调用 / N+1、无界队列、锁粒度、大事务、缓存击穿、超时与重试放大、连接池占用 |
| 业务逻辑正确性 | 边界与空值、状态机非法流转、事务一致性、幂等、需求实现偏差 |
| 安全合规 | 注入、越权、密钥硬编码、敏感数据落日志、外部输入校验 |
| 可运维性 | 吞异常、日志缺失或过量、缺超时、不可回滚、配置硬编码、缺开关 |

每条检查项都要能落到具体代码证据上。做不到这一点的检查项，最后只会变成「我觉得这段代码不太好」——这种结论对研发没有价值，还会消耗信任。

### 2.4 输出是风险假设，不是判决

Agent 给出的是「风险假设 + 证据 + 建议」，SRE 做确认。分级大致三类：

- **阻断**：证据确定且后果明确，比如硬编码密钥、明确的越权路径
- **需确认**：有证据但需要业务判断，比如新增同步调用可能影响容量
- **提示**：最佳实践和可维护性建议，不阻塞

这样分的原因很实际：AI Coding 场景下，如果每天产出上百条「可能有问题」，没人会看，方案就死了。必须把确定性的问题和需要判断的问题分开。

### 2.5 误判成本和上一类场景不同

这里误报的代价特别高。误报会让研发花时间解释、让 SRE 反复复核，几次之后大家就开始忽略告警——而忽略告警这件事，比漏掉一条风险更危险，因为它是系统性的。

所以这里不追求召回优先，而是**高置信优先**：只有能给出具体证据、能指出具体代码位置和影响路径的，才升级；风格、命名、注释这类问题只做提示，甚至不报。

证据门槛的具体做法和别的场景一样：引用必须存在、必须能回溯、置信度和证据数量要匹配。没有证据的直觉判断，宁可写成「待验证线索」。

### 2.6 最大的风险：AI 审 AI 的同源盲区

生成代码的模型和评审代码的模型，如果训练数据、偏好和知识盲区高度重合，就可能出现「AI 觉得这样写没问题，评审 AI 也觉得没问题」的情况。代码风格越一致，这种风险越隐蔽。

这是「用 AI 对抗 AI」必须正视的问题。缓解手段有几个：

- **引入独立信号**：静态规则、代码图谱、测试结果、运行时指标，这些不是模型判断，能提供交叉验证
- **用真实故障校准**：拿历史上确认过的缺陷和故障做回测，看 Agent 能不能识别
- **不同模型、不同提示策略交叉**：至少不要让生成和评审共享同一个盲区来源
- **结果不由 AI 签字**：AI 只能提出假设，确认权在人

不能把「AI 评审通过」当成正确性的证明，它只是把风险暴露得更早、更全。

### 2.7 上下文决定判断质量

| 上下文 | 回答什么问题 |
| --- | --- |
| 需求与验收标准 | 这个改动是不是实现了它该实现的东西 |
| diff 与改动范围 | 具体改了什么、改了多少 |
| 调用链与影响面 | 会影响哪些入口、依赖、数据表 |
| 测试变化与 CI 结果 | 哪些行为被验证过，哪些没有 |
| 历史相似变更与故障 | 这个模块以前踩过什么坑 |

缺任何一块，判断都会退化成看 diff。尤其是需求——没有需求，Agent 无法判断「实现偏差」，只能看到「代码写得对不对」。

### 2.8 人的角色变了，责任没变

评审人从「逐行读代码」变成「确认风险假设、做业务判断、维护检查规则」。SRE 不是被替代，而是从执行评审的人，变成校准评审标准和兜底的人。

责任边界必须清楚：AI 出报告，人签字。这一点不因为效率提升而改变。

## 三、收益与衡量

收益不在于「AI 评审比人准」，而在于：评审的吞吐能跟上代码的产出；评审的判断建立在完整上下文而不是一眼扫过的 diff 上；风险能被更早、更具体地暴露出来。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 风险检出率 | 真实缺陷中被 Agent 提出的比例 | 核心指标，直接对应漏报 |
| 高置信准确率 | 高置信结论中被确认为真的比例 | 决定报告还有没有人看 |
| 评审覆盖率 | 接入评估的 MR / 发布占比 | 风险地图的完整性 |
| 人工评审时长 | 人工评审投入的变化 | 衡量是否真的减负 |
| 缺陷逃逸率 | 上线后暴露、评审阶段未识别的问题占比 | 最终效果 |
| 采纳率 | 建议被采纳或转为改进项的比例 | 衡量是否真的有用 |
| 端到端时延 | MR 提交 → 报告产出 | 决定能否嵌进研发节奏 |

小范围验证中，实测数据待补。

## 四、结论

问题的本质不是「评审要更快」，而是评审的供给侧必须换主体。AI 把代码产出提上去了，评审如果还是靠人一行行读，这个缺口只会越来越大。

一句话总结：**让 AI 先把「读懂代码、拼齐上下文」这件事做一遍，人只做确认和判断。**

「用 AI 对抗 AI」不是让两个模型互相背书，而是用 AI 的处理能力，加上代码图谱、测试和历史故障这些独立信号，把风险暴露在人工评审还来得及处理的时候。

下一步要验证的：

1. 检查项和证据门槛能不能把误报压到研发愿意看的程度；
2. 同源盲区到底有多严重，独立信号能补上多少；
3. 合入前和发布前两层介入，是否真的比只做一层更有效。
