# 业务配置操作风险监测：变更类操作识别

> 系列：AI SRE 实践笔记 · 01
> 范围：业务配置操作风险监测的识别环节
> 状态：小范围验证中，数据待补
> 配套实践：[业务配置操作风险监测：变更类操作识别（工程实现）](../practice/01-业务配置操作风险监测.md)

## 一、问题

### 1.1 场景

业务配置操作的风险监测是一条链：

```
有哪些操作 → 哪些会改变线上状态 → 风险分级 → 管控策略（审批/灰度/熔断/观察/回滚）
```

本文只讲第一环：**变更类操作识别**——哪些操作会改变线上状态、属于哪类变更。它是后面所有动作的前提，标错了，后面的风险分级和管控就都建在错误的地图上。识别之后的环节由下游承接，不在本文展开。

我们已有的信息来自 SDK：应用、方法名、方法描述。之前由 SRE 拿这三样人工打标，投入很大，效果很差。

### 1.2 痛点

1. **信息不足。** 方法名和描述是作者对意图的压缩，不是对行为的描述。命名不规范、描述为空或过期、`handle`/`process`/`commonXxx` 大量存在时，SRE 手上的信息几乎不足以判断，只能靠猜和记忆。
2. **覆盖率与时效双低。** 人力只能覆盖被点名的重点应用和接口，长尾应用、新应用无人标，标过的迭代几次就过期；人工标注是快照式、周期式的，追不上业务迭代，加人也不解决——成本随「应用数 × 迭代次数」线性增长。
3. **没有反馈闭环。** 标错没人告诉你，漏标一个写操作往往要等它真的引发故障才被发现。判断质量无法度量，也无法改进。

典型的失效模式：

| 方法名 / 描述 | 实际行为 | 人工容易怎么判 |
| --- | --- | --- |
| `getOrderDetail` | 内部懒加载库存并回写缓存 | 只读（漏判） |
| `queryAndSync` | 查询后同步写库 | 只读（漏判） |
| `updateUser` | 只更新内存对象或写审计日志 | 变更（误判） |
| `handle` / `process` | 描述为空，实际写多张表 | 无法判断 |
| `refreshConfig` | 改的是本地缓存，不是线上配置 | 变更（误判） |

### 1.3 根因：判断依据放错了地方

不是 SRE 不努力，而是输入与判定目标错配：判定需要的是「方法执行后会不会改变线上状态」，这是一个**代码事实**；而输入只有名字和描述，是**作者意图的摘要**。真正知道方法干了什么的人（研发）不写文档、不打标；有判定责任的人（SRE）不掌握代码上下文。也没有反馈，质量不会自我修正。

把「这是什么操作」拆成三个可计算的子问题：

- **副作用**：方法最终是否触达一个会改变状态的操作（写库、发消息、改配置、调外部写接口……）
- **可达性**：从方法出发，经过调用链能否到达那个副作用，中间隔几层封装、是否在条件分支或异步回调里
- **业务语义**：这个副作用在业务上算不算「变更」（写审计日志算吗？删缓存算吗？幂等写算吗？）

前两个是代码结构问题，正好是调用图擅长的；第三个需要读实现和业务理解，是 LLM 擅长的。问题因此从「给方法名做文本分类」变成「**图上的可达性分析 + 语义裁决**」。

另外有个前提要先定下来：判定粒度是 **API 入口方法**。内部方法的调用路径和写操作只作为证据链的一部分，最终结论落在入口方法上。风险分级、管控策略本来就是按接口做的，粒度对齐之后，候选集也从全量方法收窄到了入口方法。

## 二、思考

### 2.1 为什么是「知识图谱 + Agent」

| 方案 | 信息来源 | 主要问题 |
| --- | --- | --- |
| 人工打标 | 名字 + 描述 + 个人经验 | 覆盖低、时效差、不可度量、知识随人流失 |
| 命名/注解规则 | 方法名、`@Transactional`、SQL 关键字 | 跨层封装、动态 SQL、RPC 透传导致规则补不完，准确率有天花板 |
| 研发写代码时加注解 | 作者本人 | 推行成本高、老代码无注解、可漏可绕过；适合做辅助信号 |
| 纯 LLM 看名字和描述 | 与人工相同的两三个字段 | 输入没变，只是换了个更会编的主体；不可解释 |
| **图谱 + Agent** | 代码实现、调用链、入口类型 | 工程复杂度更高；动态特性有盲区 |

关键差别不在模型，而在**信息维度**：前四种用的都是「关于代码的描述」，图谱 + Agent 用的是「代码本身」。准确率的提升来自信息变多，而不是模型比人聪明。同时，判定结果可以带证据链（哪个方法、哪一行、经哪条路径触达了哪个写操作），因而可复核、可申诉、可归因。

### 2.2 关键工程判断：先反向可达，再问模型

逐个入口方法问 LLM，成本是 O(入口方法数)，规模大一点的公司也是几十万量级的调用，既贵又慢。更合理的做法是先用图做一次性**反向可达性分析**：从所有副作用节点出发沿调用图反向遍历，给每个方法算出结构分——是否可达写操作、最短几跳、路径上有几个写节点、是否只在异常分支可达——再汇总到入口方法这一层。然后分流：

- 直接写、1~2 跳可达 → 大概率变更，抽样校验
- 不可达任何写操作 → 大概率只读，抽样校验
- 3 跳以上、条件写、只经缓存写、语义模糊 → **灰区，交给 Agent**

LLM 只处理灰区，成本从 O(入口方法数) 降到 O(灰区数)，通常降一个数量级。**「近实时」靠的是结构筛选，不是模型推理变快。**

### 2.3 判定准则必须显式化

「变更类」不是自明概念。不写清边界，Agent 判定会随样本漂移，人也没法复核。建议做成**多标签**而非二分类，因为下游管控策略不同：数据写入、配置/开关变更、流量/路由变更、权限/账号变更、消息投递、外部写调用。

必须提前定下的边界：

| 情形 | 倾向 | 理由 |
| --- | --- | --- |
| 只写审计 / 访问日志 | 不算 | 不改业务状态；合规要求另计 |
| 幂等写、dry-run、补偿 | 看是否真推进状态 | 幂等不等于无副作用，要读实现 |
| 读操作触发懒加载 / 缓存回写 | 算（轻度） | 线上可观测行为会变 |
| 缓存删除 / 刷新 | 算（轻度） | 影响下游读路径与数据库压力 |
| 读取开关 | 不算 | 无状态改变 |
| 修改开关 | 算 | 典型配置变更 |

这些判断应成为一份 SRE 与研发共同维护的**可评审 rubric**，而不是藏在 Prompt 的例子里。它的价值不只是让模型更准，更是让「什么算变更」这个组织内长期模糊的问题第一次被写下来。

### 2.4 误判成本不对称：召回优先

漏判意味着操作完全脱离管控，风险敞口无限；误判只是多一层审批，成本有限。因此优化目标是**召回优先**，而不是好看的准确率：输出置信度而非硬标签、阈值可调；高置信自动入库，中置信抽样，低置信进人工队列。人工角色从「全量标注」变成「灰区复核 + 规则维护」，投入随灰区规模变化，而灰区会随 rubric 和样本积累逐步缩小。

### 2.5 最大的长期风险是图谱腐化

图谱若不能随代码实时更新，半年后它和人工标注一样过期，只是过期得更贵。所以核心组件其实不是 Agent，而是**把图谱更新挂进研发流水线**：合并/发布事件触发增量索引；只重算受影响的子图（变更方法 + 其上游调用者）；缓存「方法体 hash → 判定结果」；维护 SDK 上报版本与 commit 的对应关系，避免「拿新版代码判断旧版行为」。要度量的是**端到端时延**（代码合并 → 标签可用），而不是模型单次推理耗时。

### 2.6 下一步与未解问题

- **线上数据补盲区**：反射、动态代理、脚本、配置驱动的调用靠静态图谱补不齐。有写流量的方法**一定**是变更类（高置信正样本），没写流量则不能反推只读。用这种弱标签校准并扩充金标集，成本低、收益明确。
- **动态特性精度**：反射、SPI、AOP、动态 SQL 下会不会出现「图上不可达但线上确实写了」的系统性漏判。
- **判定稳定性**：需要 temperature=0、固定 Prompt 版本、维护回归集，否则 Agent 本身就是一个不稳定的运营对象。
- **责任划分**：rubric 谁维护、判错谁负责？「变更类」成为发布前置条件后，误判会不会阻塞正常发布？需要申诉通道和 dry-run 能力。
- **跨应用写**：A 调 B 的写接口，A 的变更性依赖 B 的标签，需要跨应用依赖图和标签传播——单仓图谱解决不了，可能是下一阶段的主要工作量。

## 三、收益与衡量

收益不应表述为「AI 比 SRE 准」，而应落在四点：**信息维度**从 2 个字段变成代码实现 + 调用链 + 证据；**成本结构**从随迭代线性增长的人力变成一次性建设 + 边际成本趋近于零；**时效**从周/月级运营节奏变成随代码合并实时产出；**可运营性**从不可解释的标签变成带证据链、可复核、可回填的判断。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 漏判率 / 召回 | 人工金标中变更类被正确识别的比例 | 主指标，直接对应风险敞口 |
| 准确率 | 判为变更类的样本中确实为变更类的比例 | 控制误判带来的人工负担 |
| 覆盖率 | 已给出判定的入口方法 / 应覆盖的入口方法（含实体对齐率） | 风险地图的完整性 |
| 端到端时延 | 代码合并 → 标签可用 | 决定能否匹配业务迭代节奏 |
| 人工复核占比 | 进入人工队列的比例 | 决定长期人力成本 |
| 单位方法成本 | tokens + 计算 + 人力 / 方法 | 决定能否全量铺开 |

## 四、结论

这个问题的本质不是「怎么让人标得更快」，而是**判断依据放错了地方**。变更性是一个代码事实，应该由代码回答。

一句话总结：**把藏在人脑里的隐性知识，变成写在代码里的显性证据；人从标注者变成规则维护者和例外处理者。**

下一步要验证的，不是模型还能不能更准，而是两件工程问题：

1. 图谱更新能不能真正挂进流水线，做到增量、实时、不腐化；
2. 跨应用写调用的标签能不能传播，把单仓的局部正确拼成全局正确。
