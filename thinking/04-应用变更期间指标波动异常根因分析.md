# 应用变更期间指标波动异常根因分析：从「看指标」到「读代码」

> 系列：AI SRE 实践笔记 · 04
> 范围：变更观察窗口内的指标异常根因分析
> 状态：方案设计
> 配套实践：[应用变更期间指标波动异常根因分析：工程实现](../practice/04-应用变更期间指标波动异常根因分析.md)

## 一、问题

### 1.1 场景

变更期间做技术指标观测，是很常见的风险防控模式：发布后盯着 RT、错误率、CPU、GC、连接池这些指标，和基线比，异常了就决定继续放量还是回滚。

这条链路大致是：

```
变更发布 → 指标观测 → 发现波动 → 人工排查 → 判断影响 → 放量 / 回滚
```

前面几步都有工具支撑，真正卡住的是「人工排查」这一段。指标能告诉你哪里变了，但说不清为什么变。

### 1.2 痛点

1. **波动看得见，原因说不清。** 同一个 RT 上涨，可能是锁竞争、慢 SQL、线程池配置、下游超时重试、也可能是流量结构变化。指标只给现象，不给原因。SRE 判断到「某个接口变慢了」就停住了。
2. **缺少面向代码的挖掘手段。** trace 能定位到方法，但解释不了方法里的实现。SRE 对业务应用的实现方式了解有限，拿到调用链也不知道该看哪一行、哪段逻辑有问题。于是只能把问题转给研发，自己给不出有效建议。
3. **观测数据用一次就丢。** 变更期观测本来是为这一次变更的风险控制服务的，窗口一过就归档。但这些数据其实暴露了应用在服务表现上的短板——容量、并发、依赖稳定性——没有人把它变成代码级的改进项。

### 1.3 根因：观测停在现象层，代码事实没有进入分析

指标是结果，代码是原因。现在的分析链路里，缺的正是「从指标定位到代码实现」这一环。

- **信息错位**：SRE 手上有观测数据和风险判断，研发有代码上下文，两边之间没有一个共享的分析载体。沟通靠转述，转述一次丢一层信息。
- **分析不可复用**：每次异常都从头看 curve、重新找人问，结论停留在「现象描述」，不是「根因假设 + 验证方法 + 修复建议」。
- **观测与代码版本脱节**：指标是线上的，代码是仓库里的，中间没有可靠的版本对应，分析时经常拿新代码解释旧行为。

把问题拆开，其实是三个子问题：

- **哪些波动值得查**：从指标时序里识别真正的异常模式，区分噪声和信号。
- **波动落在哪段代码**：把异常指标关联到具体的实例、接口、调用链和方法。
- **为什么会波动**：结合代码实现、变更 diff、配置和依赖，给出根因假设，并用数据验证。

前两个偏数据与图谱，第三个需要读代码、懂业务语义，是 LLM 擅长的。

## 二、思考

### 2.1 为什么是「指标 + 调用链 + 代码」，而不是只看其中一样

| 方案 | 靠什么 | 主要问题 |
| --- | --- | --- |
| 阈值 / 异常检测 | 指标时序 | 只能发现异常，不能解释；告警多了就没人看 |
| 人工看曲线 + 经验 | SRE 经验 | 依赖个人，深度有限，结论不可复现 |
| 只看变更 diff 做 review | 代码 | 不知道线上实际发生了什么，抓不住异常与代码的对应关系 |
| 纯 LLM 看指标和日志 | 文本 | 缺少代码事实，只能给泛泛建议；数字和结论都不可靠 |
| **指标 + 调用链 + 代码上下文** | 三方数据 + LLM 归因 | 需要三方对齐；异步、动态特性有盲区 |

关键在分工：**指标回答「哪里异常」，调用链回答「哪条路径」，代码回答「为什么」，LLM 负责把三者串成可验证的假设。** 缺任何一层，最后都只能得到一段听起来合理但没法验证的解释。

### 2.2 关键工程判断：先定位，再归因，最后验证

一次分析分四步，顺序不能乱：

1. **异常检测**：用变更前后对比的方式识别波动，而不是简单阈值。要判断形态——突变、持续漂移、周期变化、多指标同步——以及持续时间和影响范围。
2. **异常定位**：从异常指标往下钻到实例、接口、trace span，找出耗时或错误集中的方法；同时圈定本次变更 diff 影响的方法。
3. **根因归因**：把异常方法、调用链上下游、代码实现、变更 diff、关键配置一起交给模型，生成按置信度排序的根因假设。
4. **证据验证**：每个假设都要给出可执行的验证方法——同类实例对比、回滚实验、分群对比、慢查询佐证。没有验证方法的假设，不进结论。

这里和很多 AI 分析方案的分歧在于：**模型不负责算数**。指标对比、trace 聚合、self time 计算都在确定性层完成，模型只拿结果做解释和假设生成。否则数字一旦出错，整个报告都不可信，而这类错误从报告表面根本看不出来。

### 2.3 指标判读必须先控制变量

变更期的指标波动是最容易误读的，因为混进来的因素太多：流量结构变化、滚动发布期间新旧实例并存、实例重启、缓存冷启动、下游抖动、时段因素。

几个必须写进分析规则的事情：

- **同期对比，而不是和历史平均比。** 工作日上午和周末凌晨的基线完全不是一回事。
- **滚动发布要按实例版本分组。** 新旧实例混在一起算平均值，会把差异抹平，甚至方向都反过来。典型的情况是：新实例慢，但新实例承接的流量少，整体平均值看不出来。
- **排除冷启动。** 新实例刚起来时 JIT 未预热、缓存未填充，前几分钟的指标不代表稳态，要么排除，要么单独标注。
- **分清因果方向。** CPU 高可能是 RT 上涨的结果，而不是原因。饱和度指标要结合队列、线程池、下游耗时一起看，不能直接当根因。
- **多变更叠加时不做单独归因。** 同一个窗口里发了多个变更，结论里必须标明「不可单独归因」。

这些规则不写清楚，模型很容易把自然波动解释成代码缺陷，给出一个逻辑自洽但完全错误的根因。

### 2.4 代码上下文以变更为锚点，沿调用链扩展

只给 diff 不够，因为很多问题出在 diff 之外的既有实现——本次变更只是把它放大了，比如新加了一个循环调用，把原本就慢的下游接口放大了十倍。

所以上下文这样组织：

- **锚点**：本次变更 diff 涉及的方法。
- **第一圈**：diff 方法的上游调用者，以及被它调用的下游依赖（1~N 跳）。
- **第二圈**：异常 trace 命中的方法及其所在调用路径。
- **按需扩展**：前两圈解释不了时，再沿可疑路径往外扩。

上下文里需要包含的不只是代码：线程池、超时、重试、连接池、缓存这些配置，往往才是根因所在。配置如果放在配置中心，也要一起拉进来，并标注版本。

### 2.5 输出必须是可验证的假设，不是故事

报告要能直接被研发用，结构应该包含：

- **异常摘要**：哪几个指标、什么形态、持续多久、影响哪些实例和接口。
- **根因假设**：每条带证据（trace、代码行、diff、配置值）、置信度、验证方法。
- **排除项**：查过但不成立的假设，以及为什么排除。这一项能省掉大量重复劳动。
- **代码级建议**：改哪里、怎么改，而不是「建议排查 XX 模块」这种空话。
- **数据缺口**：采样不足、没有 trace、配置缺失，都要明说。数据不足时结论是「无法判定」，不是「无异常」。

### 2.6 误判的成本和别的场景不一样

这类分析最怕的不是漏报，而是**给出一个错误但很具体的根因**。研发按错误的方向改代码、加配置，浪费的是信任——几次之后，这份报告就没人看了。

所以不能一味追求召回，要有证据门槛：

- 有代码证据、有验证方法 → 高置信，进结论
- 只有现象关联 → 标「待验证」，只作为排查线索
- 连现象都对不上 → 不输出

宁可少给几条，也要保证给出的每条都能站住。这和「先广泛召回再人工筛」的思路不同，因为这里的消费者是研发，错误的成本比遗漏更高。

### 2.7 长期风险：三方数据和代码版本的一致性

- **指标口径漂移**：指标定义、采集方式、标签维度变化，历史基线就不可比了。
- **trace 采样率不足**：长尾异常可能根本采不到，报告会系统性地偏乐观。
- **代码版本错位**：灰度、回滚、多版本并存时，拿哪个 commit 分析，必须显式记录。
- **反馈不闭环**：根因假设被研发确认或否定，如果不回填，分析能力不会提升，同样的错误会反复出现。
- **配置不在代码库**：很多根因在配置中心，代码分析看不到，需要打通。

### 2.8 观测数据的第二次利用

变更期观测的价值不止于这一次变更。把多个变更窗口的数据攒起来，能看出应用在服务表现上的稳定短板：哪个依赖总是抖动、哪类接口在流量上来时先崩、哪里的重试策略在放大故障。

这些不是「本次变更的风险」，而是应用本身的服务能力问题。把它们沉淀成技术债或优化项，变更期的观测就从一次性的风险控制，变成了持续的应用质量输入。

## 三、收益与衡量

收益不在「AI 比 SRE 会看曲线」，而在三件事：分析从现象层走到代码层；结论可验证、可复现；观测数据从一次性消耗变成可积累的资产。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 根因命中率 | 高置信根因被研发确认的比例 | 核心指标，直接反映分析质量 |
| 误报率 | 被研发否定的根因假设占比 | 决定报告还有没有人看 |
| 定位时长 | 异常发生 → 根因假设产出 | 决定能否在变更窗口内做决策 |
| 报告采纳率 | 建议被采纳或转为改进项的比例 | 衡量是否真的有用 |
| 覆盖率 | 有异常且完成分析的变更 / 有异常的变更 | 风险地图的完整性 |
| 数据完备率 | 指标、trace、代码三方齐全的变更占比 | 决定分析质量的上限 |
| 单位分析成本 | tokens + 计算 + 人力 / 次 | 决定能否全量铺开 |

本文只定义指标口径，实测数据待补。

## 四、结论

问题的本质不是「SRE 不会看指标」，而是观测数据和分析目标之间断了一环：指标代表的现象在线上，能解释现象的代码在仓库里，中间没有一条自动化的通路。

一句话总结：**让异常指标自动落到调用链和代码上，把「哪里变了」变成「为什么变、该改哪一行」。**

下一步要解决的不是模型聪明不聪明，而是三件基础工作：

1. 指标、trace、代码版本三方对齐——决定分析结果可不可信；
2. 指标判读规则显式化——决定会不会把自然波动误判成代码缺陷；
3. 根因反馈回填——决定这套分析是越用越准，还是每次都在重新猜。
