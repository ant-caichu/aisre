# 应用发版二次故障风险控制：从「没人看的复盘」到「审批时的风险证据」

> 系列：AI SRE 实践笔记 · 03
> 范围：应用发版变更的二次故障风险识别与提示
> 状态：线上运行
> 配套实践：[应用发版二次故障风险控制：工程实现](../practice/03-应用发版二次故障风险控制.md)

## 一、问题

### 1.1 场景

应用发版是变更的主要形式，也是线上故障的主要来源之一。更要命的是，很多故障不是新问题，而是重复的：同一个依赖超时、同一个连接池配置、同一个发布顺序，隔几个月换个人、换个应用，再来一次。

这类「二次故障」本可以在变更评审阶段被拦住。现在的情况是：

```
故障发生 → 复盘 → 复盘文档 → 文档库（按时间堆积）
                                  ↓
变更评审 ← SRE 凭记忆 / 临时翻文档 / 问老同事
```

复盘写得很认真，也归档得很好。问题出在从文档库到评审现场这一段——它靠的是人的记忆。

### 1.2 痛点

1. **知识在库里，但不在流程里。** 复盘文档是写给「愿意看的人」的，按时间归档。SRE 日常不会主动翻，只有在评审时隐约觉得「这个好像见过」才会去找。知识能不能被用上，取决于记忆有没有被触发；没触发，就等于不存在。
2. **临时溯源赶不上评审时效。** 一场评审可能就十几分钟。要在几分钟内从几年、上千篇文档里找到与当前变更相关的故障，还要读懂根因、对照当前方案——这不现实，于是绝大多数评审实际上跳过了这一步，直接凭经验过。
3. **人员更迭让知识断代。** 老 SRE 知道「这个应用上次发版是怎么挂的」，人也知道该在什么时候想起哪一篇。人一走，这条隐性链路就断了。文档还在，但没人知道该在哪个场景下打开它。

### 1.3 根因：知识管理和使用场景错配

复盘文档组织方式是**按时间和故障**的，而评审需要的是**按变更对象和场景**的。两边对不上，具体有四点：

- 复盘是「拉取式」的，等人来找；评审现场需要「推送式」的，知识要主动到达审批页。
- 文档是长文本，给人读没问题；评审需要的是能直接判断的风险点。
- 检索靠关键词，但「这个变更会不会触发那次故障」是语义关联，说法往往对不上。
- 知识的使用没有反馈：哪次提示被采纳、哪次遗漏导致了故障，没人记录，体系不会自我改进。

所以问题可以拆成三个：

- **关联什么**：当前变更应该关联哪些历史故障？按什么对象、什么场景关联？
- **怎么找到**：在评审可接受的时延内召回相关故障，并且不漏掉关键的那几条。
- **怎么用得上**：把历史故障翻译成针对当前变更的风险点和检查项，而不是甩几篇文档链接。

前两个是索引与检索问题，第三个是语义对齐问题。前者靠结构化索引和 RAG，后者正是 LLM 擅长的。

## 二、思考

### 2.1 为什么是「结构化索引 + RAG」，而不是直接搜文档

| 方案 | 靠什么 | 主要问题 |
| --- | --- | --- |
| 文档库关键词搜索 | 标题、正文关键词 | 说法不一致就搜不到（「连接池打满」vs「数据库连接耗尽」），还得人自己翻 |
| 纯向量检索 | 文本相似度 | 同应用、同资源的强关联反而可能被忽略；召回精度不稳；漏召回无感知 |
| 让模型记住故障 | 微调 / 长上下文 | 故障持续新增，跟不上；给不出证据；幻觉无法核查 |
| **结构化索引 + RAG** | 对象/资源/场景维度过滤召回，向量补充语义，LLM 做对照 | 依赖复盘质量和实体标注；跨应用的相似故障需要额外建模 |

关键在三层分工：**结构化索引负责「找得准、找得全」，向量检索负责「换个说法也能找到」，LLM 负责「读懂并对照当前变更」。** 缺一层都不行。

### 2.2 关键工程判断：先结构化过滤，再语义召回，最后模型对照

最直接的写法是把变更单丢进向量库搜 top-k，让模型总结。问题是召回不稳定：同一个应用上次发版挂过，这种强信号靠文本相似度未必排得上来；而它恰恰是最该被看到的。

所以召回分两步走：

1. **硬索引召回**：按变更单解析出的应用和依赖资源，直接取出该应用、该资源的历史故障。这一层不依赖语义相似度，是确定的召回底线。
2. **语义召回**：用变更内容、变更类型、发布方式与故障的根因、触发场景做语义匹配，补上「换了应用、换了说法」的同类问题。

两路结果合并去重，按「同一根因 > 同一资源 > 近期发生 > 影响面大」排序。然后才交给模型，逐条对照当前变更方案，输出哪些历史故障可能被再次触发、触发条件是否满足、需要检查什么。

这样做的另一个好处是省成本：模型只处理几十条候选，而不是全量故障库。

### 2.3 「二次故障」的匹配要落在根因和触发条件上

二次故障不是「同一个应用又出故障」，而是**同一类根因，在同一种变更动作下，被再次触发**。所以索引和匹配必须抓住三个要素：

| 要素 | 内容 |
| --- | --- |
| 故障对象 | 应用 + 依赖资源（DB、缓存、MQ、配置项、第三方依赖） |
| 触发场景 | 变更类型（代码发布、配置、扩缩容、数据、依赖升级）、发布方式（全量/灰度/滚动）、时间和流量条件 |
| 根因类别 | 容量、依赖、配置、兼容性、数据、发布流程、人为操作 |

复盘文档是统一模板，这给了很大的便利：根因、触发条件、改进项本来就是分开的字段，可以直接转成结构化索引，不需要从自由文本里硬猜。**应用一层回答「这个应用出过什么事」，资源一层回答「这个组件在我们的系统里出过什么事」，两层都要留。**

### 2.4 输出必须是能判断的风险点，不是文档列表

评审人需要的是「这次变更哪里可能出问题」，而不是「这里有 8 篇相关文档」。所以输出应该包含：

- 关联到的历史故障：时间、应用、影响面、根因一句话
- **为什么相关**：是同一个对象、同一个资源，还是同一个触发场景
- 对当前变更的具体风险点：比如「上次故障是连接池上限低于实例数 × 并发，本次变更同时调整了实例数，需要核对新上限」
- 建议检查项：从历史改进项转译成这次可执行的检查动作
- 置信度与缺失信息

还有一条容易被忽略：**没召回时也必须明确说「未找到相关历史故障」，而不是留白。** 空白会被审批人理解成「没有风险」，但实际可能只是索引没覆盖、复盘没写、实体没对上。

### 2.5 阻断和加签的边界

高风险变更要阻断或加签，但这件事不能全交给模型判断。

| 判断来源 | 适用 | 处置 |
| --- | --- | --- |
| 硬规则 | 同应用 + 同资源 + 同类变更，且历史上由这类变更引发过故障 | 阻断或强制加签 |
| 硬规则 | 关联故障的改进项仍未闭环 | 加签，要求说明闭环情况 |
| 模型判断 | 语义相关、场景相似，但对象不同 | 风险提示，不阻断 |
| 无召回 | 未命中任何历史故障 | 正常流转，记录「未召回」 |

硬规则负责确定性强的场景，模型负责解释和补充。两者冲突时以硬规则为准。

还有一个反向风险：阻断太多，审批人会想办法绕过——线下先确认好、或者把变更拆小、或者改个说法。这种绕过比漏报更隐蔽。所以阻断必须有申诉和豁免通道，豁免原因要留痕，豁免率要当成指标看。

### 2.6 最大的长期风险是知识库本身的质量和时效

方案的上限不在模型，在知识库。

- **复盘质量决定上限。** 根因写成「操作不当」「沟通不畅」的复盘，入库之后也帮不上忙。模板有了，还得有人对字段质量负责。
- **入库时延决定保护效果。** 一次故障从发生到复盘入库如果拖了两周，这两周里所有同类变更都在裸奔。
- **实体对齐决定召回率。** 应用名、资源名在复盘、CMDB、变更单里叫法不一致，索引就对不上。这是最容易低估的工作量。
- **反馈闭环决定能不能变好。** 提示被采纳了多少、豁免了多少、有没有漏报——这些不记录，库会越用越旧。

### 2.7 知识管理模式的转变

这件事的本质，是把知识管理从「人找知识」改成「知识找人」：复盘不再只是归档，而是变成变更审批的一个输入；经验不再依附于某个人的记忆，而是跟着对象和场景走。

人在这套体系里的角色也变了：从「凭经验评审」变成「维护知识标准、处理例外」。人员更迭的影响因此从「知识断代」降到「标准需要交接」。

## 三、收益与衡量

收益不在于「AI 比 SRE 懂历史」，而在于三件事：历史经验第一次进入了变更流程，而不是躺在文档库里；风险提示变得可解释、可追溯；知识的使用有了反馈，能持续修正。

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 召回准确率 | 提示的故障中确实与当前变更相关的比例 | 决定审批人是否愿意看 |
| 漏召回率 | 事后确认相关但当时未提示的比例 | 核心指标，直接对应二次故障风险 |
| 提示采纳率 | 检查项被确认执行、风险被采纳的比例 | 衡量提示是否真的有用 |
| 豁免率 | 被阻断或加签后又豁免的变更占比 | 过高说明规则过严或流程被绕过 |
| 端到端时延 | 变更单提交 → 提示展示 | 评审场景对时延很敏感 |
| 知识覆盖率 | 已结构化索引的故障 / 全部故障；已接入的应用 / 全部应用 | 风险地图的完整性 |
| 入库时延 | 故障发生 → 复盘可检索 | 决定新教训多久能起作用 |
| 二次故障发生率 | 同类根因重复引发故障的比例 | 最终业务结果，但归因需要谨慎 |

受数据敏感性限制，本文不披露具体业务数值。以上指标在团队内部持续跟踪。

## 四、结论

问题的本质不是「文档写得不够好」，而是知识的管理方式和它的使用场景对不上：文档按时间和故障组织，评审需要按对象和场景；文档等人来查，评审需要知识自己送上门。

一句话总结：**把复盘从归档物变成审批输入，让每一次类似变更都自动带上历史故障的检查项。**

下一步要处理的不是模型能力，而是三件基础工作：

1. 复盘字段质量与实体对齐——决定召回率的天花板；
2. 新故障的入库时效——决定新教训什么时候开始生效；
3. 提示的反馈闭环——决定这套东西是越用越准，还是越用越旧。
