# 变更值守灰度过程推进决策辅助：工程实现

> 系列：AI SRE 实践笔记 · 10
> 范围：应用发布与配置开关的多阶段灰度推进判定
> 状态：小范围验证中，数据待补
> 背景与判断：[问题与思考](../thinking/10-变更值守灰度过程推进决策辅助.md)

## 0. 范围与前提

本文实现灰度阶段的自动判定：在每阶段观察窗口结束时，对比灰度组与对照组、历史同期基线和业务指标预期，输出阶段判定卡和建议，由变更人决定推进、继续观察或回滚。

**输入**：

**非目标**：不执行推进、暂停或回滚；不做根因分析；不预测容量；不定义业务指标口径（以指标注册表为准）；不替代变更人的决策责任。

**前提**：

- 有指标平台，能按灰度组和对照组分别取数
- 应用指标和业务指标已注册，口径、方向和正常范围可查
- 变更单包含阶段计划（批次、流量比例、观察窗口）
- 有至少四周的历史数据用于建立同期基线
- 发布平台和开关平台能提供当前阶段和分组信息

## 1. 总体链路

```mermaid
flowchart LR
    A[变更单/阶段事件] --> B[阶段与分组建模]
    B --> C[指标采集<br/>灰度组/对照组]
    C --> D[基线计算]
    D --> E[统计检验]
    E --> F[变更上下文与预期]
    F --> G[Agent 综合判定]
    G --> H[证据校验]
    H --> I[阶段判定卡]
    I --> J[变更人决策]
    J --> K[推进/观察/回滚]
    K -.回填.-> L[评测与校准]
```

四个环节决定成败：

1. **分组与口径**：灰度组和对照组划错，后面全是错的对比。
2. **统计显著性**：样本不足时硬判，是误停和漏判的主要来源。
3. **预期方向**：不结合变更内容，会把预期内的变化报成异常。
4. **输出压缩**：只建议不执行，报告必须让人快速确认。

## 2. 实现步骤

### 2.1 变更与阶段建模

| 类型 | 灰度维度 | 对照组 | 阶段推进条件 |
| --- | --- | --- | --- |
| 应用发布 | 版本标签、实例批次、流量比例 | 未升级实例或稳定版本 | 本批观察窗口结束且判定通过 |
| 配置推送 | 配置项 + 生效范围（实例/机房/比例） | 未推送实例 | 同上 |
| 特性开关 | 开关 key + 放量比例或白名单 | 关闭组 | 同上，需注意上下游传导 |

**阶段定义**统一成：

```text
stage_index, planned_traffic_pct, window{start,end}, completed,
gray_selector, control_selector, previous_stage
```

**分组校验**：灰度组与对照组不能在同一个故障域内互相影响（同机房、同数据库主库），否则对比不成立。校验不通过时标记 `group_invalid`，只输出单组趋势，不做组间比较。

**配置与开关的特殊性**：放量可能不改变实例，只改变行为，所以分组要按「生效配置」而不是「实例」划。开关放量还可能引起下游流量变化，这类传导要写进 `expected_effects`。

### 2.2 指标注册表与口径

每个指标必须注册以下字段：

| 字段 | 说明 |
| --- | --- |
| `metric_id` | 唯一标识，含层级前缀，如 `app.http.error_rate` |
| `layer` | basic / application / business |
| `unit`、`aggregation` | 单位与聚合方式（均值、分位、比率） |
| `direction` | higher_better / lower_better / neutral |
| `min_sample` | 判定所需最小样本量 |
| `lag_sec` | 数据延迟，业务指标常见分钟级 |
| `expected_range` | 业务指标的正常波动区间及来源 |
| `seasonality` | 是否按小时、星期几对齐 |
| `owner`、`version` | 口径负责人与版本 |

**口径变更要版本化**。同一个 `metric_id` 的口径变了，历史基线就不再可比，必须标记断点，避免拿新口径的数据和旧口径的基线比较。

**没有注册的指标不参与判定**，只在报告里作为参考数据展示，不进入结论。

### 2.3 采集与对齐

- **分组取数**：按 `gray_selector` 和 `control_selector` 分别拉取，维度保持一致
- **窗口对齐**：只取观察窗口内的数据，排除发布刚开始的预热期（连接建立、缓存冷启动）
- **聚合粒度**：基础和应用指标按分钟，业务指标按注册的聚合粒度
- **数据完整性**：窗口内缺失超过阈值，标记 `partial`；业务指标未过 `lag_sec` 不参与判定
- **口径一致**：灰度组和对照组必须使用同一版本的指标定义

**预热期单独处理**：发布后前几分钟的指标通常不代表稳态，直接纳入会制造假异常。预热时长按应用类型配置，并在报告里注明已排除。

### 2.4 基线与统计检验

**三类对比分别计算：**

| 对比 | 方法 | 输出 |
| --- | --- | --- |
| 灰度组 vs 历史同期 | 过去 4 周同一星期几、同一时段的窗口中位数与 MAD | 稳健 z 分数 |
| 灰度组 vs 对照组 | 比率类用 Wilson 置信区间，计数类用率比 | 差异及置信区间 |
| 灰度组 vs 上一阶段 | 同口径直接比较，关注趋势方向 | 变化方向与幅度 |

**计算约定**：

- 基线用中位数和 MAD，不用均值，减少历史异常点影响
- 历史窗口剔除已知故障和变更时段，避免基线被污染
- 比例类指标必须带样本量和置信区间，不比较裸比率
- 多指标同时检验时做多重比较校正，或限制参与判定的指标数量
- 趋势判断要求连续多个窗口同向偏离，单点跳变不算趋势

**判定阈值**：统计显著 + 业务影响两个条件同时满足才判 `anomaly`。只有统计显著、幅度很小，判 `watch`。样本不足判 `insufficient`，不参与维度结论。

### 2.5 变更上下文与预期方向

**预期来源**：

- 变更单中显式声明的 `expected_effects`
- 按变更类型推导的默认预期：发布可能带来资源开销变化；开关打开可能带来下游调用上升；配置调整可能改变特定行为
- 历史相似变更的实际表现（仅作参考，不作为豁免依据）

**使用方式**：

1. 预期方向只影响「解释」和「严重程度」，不豁免统计检验。预期内的变化也要看幅度是否合理。
2. 预期幅度明显超出声明时，仍判 `watch` 或 `anomaly`。
3. 变更说明含糊、没有声明预期时，不做豁免，按普通异常处理。
4. 出现声明之外的指标变化，进入 `unexpected_changes`，即使幅度不大也要提示。

**推导要克制**：只对确定的传导关系做推导（如开关关闭 → 下游调用下降），不根据业务常识猜影响面。

### 2.6 Agent 判定协议

统计结果由代码算好，模型只做组合判断和解释。

**Prompt 骨架：**

```text
你是灰度变更的指标判定助手。输入是一个灰度阶段的指标统计结果、
变更上下文和阶段信息。请判断本阶段是否在预期内。

规则：
1. 所有数值只能引用输入中的统计结果，不得自行计算、估算或补全。
2. 每条结论必须引用 metric_id 和对应的统计结果；没有统计结果的指标
   不得出现在结论中。
3. 样本不足的指标只能标记为数据不足，不得据此判断正常或异常。
4. 业务指标恶化优先于技术指标正常：即使应用层正常，业务指标低于预期
   区间也要判为异常或观察。
5. 预期内的变化也要核对幅度；超出声明范围时不得豁免。
6. 多指标结论冲突时判为观察，并列出冲突项，不要折中成通过。
7. 不下根因结论，不推测变更导致了什么；措辞限定为「指标相对基线偏离」。
8. 数据延迟导致窗口不完整时，降低 confidence，并写入 limitations。

输入：
<stage>{...}</stage>
<change_context>{...}</change_context>
<statistics>{...}</statistics>
<data_status>{...}</data_status>

输出 JSON，字段遵循给定 schema。
```

**输出校验**：

- 引用的 `metric_id` 必须存在于输入
- 引用的数值必须与统计结果一致，偏差超过容差则整条丢弃
- `anomaly` 必须有统计显著结果 + 至少一个业务或应用层佐证
- `rollback_candidate` 必须有多窗口同向恶化，不接受单点触发
- `pass` 不能与其他维度的 `anomaly` 同时作为阶段结论
- 预期豁免必须引用 `change_context.expected_effects` 的具体条目
- 校验失败 → 重试一次 → 仍失败则输出纯统计判定卡（不含解释）

**稳定性**：temperature=0，固定模型、Prompt 和指标注册表版本，写入报告。

### 2.7 判定卡与展示

**首屏**：

```text
阶段 2/4 · 10% 流量 · 观察 30 分钟
结论：建议观察（置信度：中）
原因：应用层指标正常；订单创建延迟上升 12%，在声明预期方向内；
      业务指标数据延迟，窗口未完整
需要你确认：业务指标补齐后是否恢复；下游库存服务 QPS 是否接近上限
```

**下钻**：按维度展开指标列表，每项展示灰度值、对照组值、历史基线、差异、检验方法和样本量。

**阶段历史条**：展示前几个阶段的结论和关键指标趋势，帮助判断是持续恶化还是单阶段波动。

**颜色使用克制**：红色只用于 `anomaly`，黄色用于 `watch` 和 `undetermined`。样本不足不要标红，避免制造不必要的紧张。

### 2.8 人机协作与回填

| 人工动作 | 记录 |
| --- | --- |
| 确认建议 | 推进 / 继续观察 / 回滚，记录时间 |
| 覆盖建议 | 覆盖方向 + 原因分类（经验判断、业务背景、指标口径问题、AI 误判） |
| 补充信息 | 补充的变更上下文或指标说明 |

**回填内容**：

```json
{
  "change_id": "...",
  "stage_index": 2,
  "ai_verdict": "watch",
  "human_decision": "proceed",
  "overridden": true,
  "reason_category": "business_context",
  "reason": "业务指标延迟已确认，补齐后正常",
  "incident_after": false
}
```

覆盖原因优先用于改指标注册表和判定规则，其次才是改 Prompt。

### 2.9 评测

**回放集**：历史灰度变更的阶段数据 + 当时的人工决策 + 事后是否发生故障。

| 指标 | 计算方式 |
| --- | --- |
| 判定一致率 | AI 结论与人工最终结论一致的比例 |
| 异常召回率 | 人工确认异常的阶段中被提示的比例 |
| 误停率 | 判为异常但人工确认正常的比例 |
| 提前发现时间 | AI 提示异常 → 人工确认的时间差 |
| 数据不足率 | 判为 undetermined 的阶段占比 |
| 判定稳定性 | 同一输入重复判定的结论一致率 |
| 建议采纳率 | 人工采纳推进/观察/回滚建议的比例 |
| 阶段耗时 | 窗口结束 → 人工决策 |

**分层**：按阶段序号、变更类型、应用等级、时段分层。第一阶段和夜间是薄弱环节，单独看召回率。

**回放要求**：使用当时可见的数据，不能用事后数据补全，否则评测结果会虚高。

### 2.10 运行与成本

- **触发**：阶段窗口结束时触发完整判定；窗口内可按固定间隔做轻量检查，只输出统计异常，不调用模型
- **耗时**：取数 → 基线 → 统计 → 模型 → 校验。取数是主要瓶颈，基线和历史窗口可预计算缓存
- **缓存**：历史基线按「指标 + 星期几 + 时段」缓存；指标注册表变更时失效
- **降级**：模型不可用时输出纯统计判定卡；业务指标缺失时只判技术维度，并明确标注
- **成本**：每阶段一次模型调用；窗口内的轻量检查不调用模型
- **权限**：指标和变更信息按应用权限控制；判定记录进入变更审计

## 3. 小范围验证

目前在部分应用和部分变更类型上试用，覆盖应用发布和配置开关两类灰度。受数据敏感性限制，不披露具体数值。

验证重点：

1. **判定是否可信**：人工是否愿意根据判定卡做决定，误停率能否接受。
2. **早期阶段是否可用**：第一阶段样本少，判定是否大部分落在「数据不足」。
3. **预期识别是否准确**：声明了预期方向的变更，是否还会被误报。

试用中确认的几个判断：

- 只给技术指标，业务指标异常经常被漏掉；业务指标接进来之后，判定质量提升明显。
- 不结合变更上下文时，预期内的延迟上升和资源变化会被反复报成异常。
- 样本量不足时老实说「数据不足」，比硬给结论更容易被接受。
- 判定卡上「需要你确认」这一栏，比长篇分析更影响使用意愿。

## 5. 已知边界与坑

| 问题 | 影响 | 应对 |
| --- | --- | --- |
| 早期样本不足 | 误判或大量 undetermined | 最小样本 + 延长观察建议，不硬判 |
| 业务指标延迟 | 窗口结束数据未到齐 | 按 lag 对齐，标 limitations，不提前下结论 |
| 分组不纯 | 灰度组和对照组互相影响 | 分组校验，失败时不做组间对比 |
| 历史基线被污染 | 基线偏移，异常识别失真 | 剔除故障和变更时段，用中位数和 MAD |
| 大促与节假日 | 同期基线不适用 | 标记特殊时段，降低置信度，改看组间对比 |
| 口径变更 | 新旧数据不可比 | 注册表版本化，口径断点标记 |
| 多重比较 | 指标多，必然有一个显著 | 校正或限制指标数量 |
| 预期声明过宽 | 真异常被当成预期内 | 预期只解释不豁免，幅度超限仍报 |
| 变更说明含糊 | 无法判断预期 | 不做豁免，按普通异常处理 |
| 单点跳变 | 误报 | 要求多窗口同向，单点不判异常 |
| 业务指标恶化但技术正常 | 漏判 | 业务优先原则，业务异常必须提示 |
| 判定被当成自动推进 | 责任边界模糊 | 明确只建议，决策记录留痕 |
| 误停累积 | 团队不信任 | 异常需双维度佐证，颜色使用克制 |

## 6. 下一步

1. **业务指标治理**：优先统一核心业务指标的口径、延迟和正常区间，这是判定质量的上限。
2. **窗口内实时检查**：在阶段结束前发现持续恶化，缩短发现时间，同时避免单点误报。
3. **预期方向库**：把历史变更的预期与实际变化沉淀成可复用的模式，减少对变更说明质量的依赖。
4. **分级自动推进**：对低风险、指标稳定、历史一致率高的变更类型，试点自动推进，回滚仍由人确认。
5. **判定质量运营**：按应用和变更类型统计误停与漏判，形成定期复盘机制。
