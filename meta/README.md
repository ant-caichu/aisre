# Meta - AI SRE 思考与实践

本目录收录 SRE 工作中遇到的问题，以及如何用 AI 解决这些问题的思考与实践。每篇实践由两篇文档组成：`thinking/` 讲为什么这么做、边界在哪里；`practice/` 讲具体怎么落地。

## 项目目标

- **问题驱动**：从真实 SRE 场景出发，不写脱离场景的方案
- **判断优先**：重点记录取舍和边界，而不只是功能描述
- **可落地**：给出输入输出、协议、校验和评测方式
- **可复用**：把方法沉淀成可迁移的模式，而不是一次性脚本

## 分篇摘要

### 01 业务配置操作风险监测
- **问题**：业务配置变更的影响面靠人判断，配置项与代码入口之间的链路不清，漏判误判都常见。
- **做法**：SDK 采集配置元数据，用代码知识图谱做反向可达，定位到 API 入口方法级别；组装上下文交 Agent 判定，支持增量更新。
- **文档**：[问题与思考](../thinking/01-业务配置操作风险监测.md) · [工程实现](../practice/01-业务配置操作风险监测.md)

### 02 风控规则变更业务验证
- **问题**：规则更新频率高，验证逻辑依赖研发临时写 SQL，结果靠人工分析，评估深度和时效都跟不上。
- **做法**：验证逻辑模板化、参数化，影子双跑产出结果；指标注册表统一口径，Agent Skill 以对话方式做业务影响评估，硬规则兜底。
- **文档**：[问题与思考](../thinking/02-风控规则变更业务验证.md) · [工程实现](../practice/02-风控规则变更业务验证.md)

### 03 应用发版二次故障风险控制
- **问题**：历史故障经验停在复盘文档里，发版评审时没人看，临时溯源又来不及。
- **做法**：复盘按统一模板结构化入库，以故障对象和场景建索引；变更审批时双路召回，模型对照当前方案输出风险提示，高风险阻断或加签。
- **文档**：[问题与思考](../thinking/03-应用发版二次故障风险控制.md) · [工程实现](../practice/03-应用发版二次故障风险控制.md)

### 04 应用变更期间指标波动异常根因分析
- **问题**：指标波动只是表象，SRE 不熟悉应用实现，难以给出研发侧可执行的根因和建议。
- **做法**：变化点检测定位异常区间，trace 与自耗时定位到方法，结合 diff 和调用链由 Agent 提出归因假设，用证据门槛约束结论。
- **文档**：[问题与思考](../thinking/04-应用变更期间指标波动异常根因分析.md) · [工程实现](../practice/04-应用变更期间指标波动异常根因分析.md)

### 05 应用 AI Coding 代码变更风险评估
- **问题**：AI Coding 让代码产出速度和变更量超出人工 Code Review 的能力，发布风险控制失效。
- **做法**：合入前和发布前两个触发点，基于需求、diff、代码图谱、测试和历史故障做四维诊断；AI 出结论、SRE 确认，并专门评测 AI 审 AI 的同源盲区。
- **文档**：[问题与思考](../thinking/05-应用AICoding代码变更风险评估.md) · [工程实现](../practice/05-应用AICoding代码变更风险评估.md)

### 06 数据库 SQL DDL 变更风险识别和提示
- **问题**：DDL 风险高，评估依赖 DBA 经验，表状态、负载、版本信息分散，人工审核被动且深度不稳。
- **做法**：SQL 解析 + 元数据采集 + 确定性估算（online DDL 能力、耗时、空间、复制），Agent 负责组合判断；硬规则可独立阻断，执行前重新校验事实。
- **文档**：[问题与思考](../thinking/06-数据库DDL变更风险识别和提示.md) · [工程实现](../practice/06-数据库DDL变更风险识别和提示.md)

### 07 系统组件变更风险识别和提示
- **问题**：ITSM 只给预案链接，知识到执行之间缺一次「针对本次变更」的翻译，效果依赖变更人熟练度。
- **做法**：按组件、对象、场景、窗口和业务重要性检索手册与复盘，直接组装步骤、风险、回滚和通知；组件按知识密度分级，引用可追溯，支持对话追问。
- **文档**：[问题与思考](../thinking/07-系统组件变更风险识别和提示.md) · [工程实现](../practice/07-系统组件变更风险识别和提示.md)

### 08 黑屏运维操作风险评估
- **问题**：堡垒机记录了命令，但数量决定了人工审不了；出事后按主机和时间翻日志，溯源慢。
- **做法**：会话切段、命令指纹、场景还原（对象 + 动作 + 意图），规则产出风险信号，按对象和时间建索引支撑应急反查；不做实时阻断，也不做违规判定。
- **文档**：[问题与思考](../thinking/08-黑屏运维操作风险评估.md) · [工程实现](../practice/08-黑屏运维操作风险评估.md)

### 09 故障复盘材料快速生成
- **问题**：应急会议材料杂乱，人工拼时间线耗时且质量不稳；定级定责容易受会议话语权影响。
- **做法**：转写和截图清洗后做时间归一、事实抽取与证据挂接，根因只整理不判定；定级由规则计算，定责只到环节和团队；产出飞书草稿，人工确认。
- **文档**：[问题与思考](../thinking/09-故障复盘材料快速生成.md) · [工程实现](../practice/09-故障复盘材料快速生成.md)

### 10 变更值守灰度过程推进决策辅助
- **问题**：多阶段灰度需要人持续盯盘，判断依赖经验，多指标冲突时缺少可核对的依据。
- **做法**：灰度组与对照组、历史同期基线、阶段间对比、业务指标预期四类依据，统计检验后由 Agent 综合判定；输出阶段判定卡和建议，只建议不执行。
- **文档**：[问题与思考](../thinking/10-变更值守灰度过程推进决策辅助.md) · [工程实现](../practice/10-变更值守灰度过程推进决策辅助.md)

## 贯穿各篇的共同判断

1. **事实与判断分离。** 能确定性计算的（元数据、指标、命令、规则匹配）交给代码，模型负责组合与解释，避免不可复核的数字进入结论。
2. **结论必须有证据。** 每条发现能指回具体字段、命令、代码行、发言片段或历史事件；没有依据的内容只能进「待确认」。
3. **人负责最终决策。** AI 出报告、建议和判定，签字、定级、定责、回滚仍由人确认，责任边界不因自动化程度改变。
4. **分级比准确率更影响可用性。** 高风险少而准、中风险聚合、低风险不打扰；误报累积会直接导致方案被绕过。
5. **反馈闭环决定长期效果。** 人工确认、误报原因和实际结果要回填，用来改规则、口径和知识库，而不是只改 Prompt。

## 内容组织

### thinking/
每个实践一篇，结构为「一、问题 / 二、思考 / 三、收益与衡量 / 四、结论」，重点回答为什么做、边界在哪、代价是什么。

### practice/
每个实践一篇，结构为「0. 范围与前提 / 1. 总体链路 / 2. 实现步骤 / 线上或验证情况 / 演进 / 已知边界与坑 / 下一步」，给出输入输出、协议、校验和评测。

### skill/
可复用的技能与模板。目前尚未沉淀独立内容，后续从实践中抽取。

## 写作与数据约定

- **独立性**：各实践彼此独立，可以单独阅读，文档之间不做交叉引用。
- **数据敏感性**：不披露具体业务规模、效果数值和内部指标；涉及线上运行的部分只描述机制与形态。
- **状态标记**：文首标注范围与状态，状态变化时同步更新对应 README 和本页清单。
- **命名**：`0N-<实践名称>.md`，编号按创建顺序，thinking 与 practice 同名对应。

## 如何使用

1. 先看本页清单，按问题场景找到对应实践；
2. 读 `thinking/` 了解判断和边界，确认是否适用于自己的场景；
3. 读 `practice/` 获取输入输出、流程和实现细节；
4. 状态为 `方案设计` 的篇章只作为思路参考，不建议直接照搬。
